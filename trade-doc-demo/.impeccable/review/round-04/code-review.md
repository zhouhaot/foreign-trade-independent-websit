### [MEDIUM · Resolved] 派生金额未完整检查 Number 无损往返

首轮位置：`js/utils.js:154`～`:160`、`:194`～`:198`；相关客户聚合 `js/views-fin.js:266`。已将具体复现和建议发送中枢。

共享解析校验输入、总额和已收的安全整数分及 Number 往返，但每行金额、余额差额和客户合计只检查安全整数。除以 100 后，并非每个安全整数分都能由当前 Number/格式化路径保持原分值。

- 合法订单一行 `qty=1, price=90071992547309.92`，已有同币种收款 `0.01`：总额分 `9007199254730992`、已收分 `1`，精确未收分 `9007199254730991`；首轮结果仍 `ok=true`，`outstanding=90071992547309.9`，显示 `90,071,992,547,309.90`，实际精确余额应为尾数 `.91`。对展示值重新 decimalInput 得到分 `9007199254730990`，少一分。
- 明细 `[{qty:3,price:30023997515769.03},{qty:1,price:0.01}]`：首轮 `transactionAmounts` 返回成功，首行精确分 `9007199254730709`、总额分 `9007199254730710`。首行 `/100` 后显示尾数 `.10`，精确应 `.09`，导致首行显示已等于总额，第二行仍有 `.01`，可见金额不勾稽。

两例由审查代理独立 Node VM 加载真实 helper 复现；没有改正式 Mock 源码。建议所有要显示/保存的派生金额逐项验证往返，不支持时返回具名错误、保留精确分字段并停止新增；客户合计同样检查。极端大额边界，因此评级 MEDIUM，不夸大为常见交易丢款。

修正回读：中枢对每行金额和余额/超收差额执行 Number→decimalInput→整数分往返检查；不支持显示时 `ok=false`、派生展示值为 NaN，仍保留可计算的精确分值，`orderFin.balance/overpaid` 不再重新对未经检查的分值做除法。客户汇总也比较 `aggregate.units===b.cents`，失败显示“汇总待核对”和完整范围原因。

审查独立重跑原两例：首行 `.09→.10` 的候选被拒绝、rowIndex=0、返回空候选明细；原余额例 `balanceCents=9007199254730991` 保留，balance/outstanding/overpaid 展示均 NaN，错误明确不能无损显示，兼容 orderFin 同样不输出失真余额。新增 decimal 回归覆盖行、余额及超收派生值，财务回归覆盖客户聚合，均独立 PASS。其他数字审查代理对同根因给 HIGH；本报告保留自己的 MEDIUM 评级和复现，不替换或删除其独立材料。

### [MEDIUM · Resolved] 收款未绑定同账号的新会话对象

修正回读：财务提交捕获 `actorReference`，延迟回调同时比较原用户引用、ID/姓名和财务角色。审查独立重跑原会话复现场景：完整 MOCK 不变、inline 明确会话改变、金额原文 `1.00` 保留、没有成功提示和重绘。新专用财务回归亦覆盖同字段新对象，已通过。
