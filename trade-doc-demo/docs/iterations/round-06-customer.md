## 现实问题与 RED 证据

旧客户保存仅校验五项必填，提交时从当前 `location.hash` 猜客户，然后逐字段写入。真实原生 submit 监听器的隔离复现中，表单来自 C001，账号换成管理员且路由变为 C002，提交把 C002 中文名改为「管理员错写」，其英文名、联系资料又被 C001 输入覆盖；C001 没有因此成为正确目标。新测试在修改运行代码之前首先得到「失败全 MOCK 零写入」断言 RED，证明按钮隐藏和当前路由不能作为原资料写入资格。

邮箱仅必填、等级未限定，同样不能保证客户资料基本格式。若后面的字段无效，逐项赋值也难以给出完整候选和统一拒绝边界。

## 明确假设与边界

- 本地 token 是表单上下文票据，不是服务器身份凭据，也不是防篡改证据。权限与一次保存仅在当前静态原型内校验。
- 邮箱仅基本结构检查，支持常见 plus 地址，不做 DNS、投递、邮箱所有权或完整 RFC 校验；真实企业邮箱政策仍待确认。
- 电话是可选的单行可读文本，保留国际号码、分机及客户原有书写；地址是可选单行文本，备注是可选多行文本。没有猜测号码格式、客户姓名规则、国家字典或业务长度上限。
- 保存前 trim 前后空白；失败时原始 DOM 输入保留，成功后按候选规范化。没有自动保存或持久化，刷新仍恢复样例。
- 既有「新建客户」仍为明确的演示占位动作，需主数据接入后另行设计；本轮只维护已存在客户，没有悄悄开放新增功能。

## GREEN 验证与复盘

新脚本 51 场景 PASS，运行实际原生 submit 监听器，使用最小 DOM 隔离桩与完整 MOCK 对照。覆盖角色/会话/对象/内容/表单/路由绑定、完整候选原子拒绝、文本/邮箱/等级、失效票据、错误后重试、一次成功/重复无第二反馈、历史交易与快照不变。可读文本被 HTML 转义，`<script>` 作为纯文本保存后仍转义展示；3000 字备注与国际电话文字可保存，未增加猜测长度限制。

邻近独立回归：`verify-views.cjs` 100 角色视图与既有业务动作 PASS；`verify-context-navigation.cjs` 194 合法上下文 + 15 成功 clean/失败 dirty PASS；`verify-navigation-drafts.cjs` 33、登录与会话脚本 PASS。所属 JS 语法与差异检查在交付时核对。

本 agent 没有执行浏览器布局/键盘/读屏、file://、真实邮箱验证、服务器身份/事务/审计、NAS 或持久化，不把隔离脚本通过等同于这些验收。中枢将继续真实交互和不同视角测评。

本次经验是保存目标必须来自打开资料时明确绑定的客户，而不是提交时偶然所在的路由；完整候选使所有输入一起通过或一起拒绝，失败后业务员能沿原输入修正。下一步是中枢 UI 与代码审查；新增客户/正式字段政策另列，避免把原型假设当公司规则。
