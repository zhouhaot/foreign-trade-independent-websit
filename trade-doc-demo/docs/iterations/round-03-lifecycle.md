# 第 3 轮单证生命周期与动作防错说明

日期：2026-10-07。基线：`main ef83c20`。单证 agent 负责 `js/utils.js` 的共享资格、`js/views-docs.js` 的动作区、`scripts/verify-document-lifecycle.cjs` 及本说明。中枢负责单证页面与操作区界面、finance 取消/重新制单处理、旧回归的 H10 适配、浏览器评测、交接与 GitHub 回执。

## 1. 动作审计与实际问题

第 2 轮已冻结交易快照，但业务动作的资格仍分散：保存仅看角色和单证状态；送审、重新制单申请、审核动作缺少完整入口校验；导出演示只看单证“已通过”，取消订单和历史旧版也能触发。部分确认框用回调执行时的当前操作者，打开后换角色或单证发生变化仍可能写入。导出先留痕、后定时 Toast，期间取消或失败也可能提示已导出。

新增专用脚本先在未修复代码运行，首次业务红灯为“解释具体订单状态”：取消申请中直接调用制单动作未按订单资格拒绝或说明原因。随后补统一资格和执行前重查，脚本由红灯转绿灯。所有验证使用样例数据，非真实业务资料。

## 2. 本轮明确的原型假设

按本轮规划契约采用 H09–H11；这是可撤销的演示策略，未声称已取得真实企业制度确认。

- **H09：取消两态暂停业务。** live 订单为“取消申请中”或“已取消”时，单证保存、送审、修订、重新制单申请、审核和导出演示全部拒绝；历史 `status`、快照和留痕保持原事实，不改写成“作废”。读取历史内容仍可进行。
- **H10：只处理最新版本。** 按同订单 `orderId` + 单证类型 `type` 确认最高版本。旧版只读，不编辑、不审核、不修订、不导出。最高版本已通过时，业务员/单证员/财务/主管可导出演示；管理员无业务导出动作。存在多个单证编号或最高版本重复时阻断，不猜哪个有效。
- **H11：现有申请保留。** 取消或出现新版后，原待审/重新制单申请仍留存，但不能继续完成失效对象的业务批准；finance 的审批拒绝由中枢集成同一资格。已退回最新版本只允许一条待处理的重新制单申请。

若正式制度允许历史凭证下载、历史版生成修订或取消过程中有限操作，应独立修改相应策略、页面说明及回归矩阵，保留快照和历史审核事实，不以覆盖版本来实现。

## 4. 共享接口契约

```javascript
U.documentPolicy(doc, user) // 无写操作；order/latest 均为当前内存中的 live 引用
// {
//   order, latest, isLatest,
//   orderBlocked, versionConflict, blockedReason,
//   canEdit, canSubmit, canRevise, canReform, canAudit, canExport,
//   reasons: { edit, submit, revise, reform, audit, export }
// }
```

- `blockedReason` 表示对象缺失、关联订单缺失、取消、版本冲突或历史版等通用原因；允许时空串。角色/单证状态/自制自审等细分原因在 `reasons[action]`；对应 `can*` 仅在原因空串时为 `true`。
- `versionConflict=true` 时 `latest=null`、`isLatest=false`。多编号、最高版重复或无效版本号不自动修正。
- 客户/商品/价格等纸张内容仍取不可变 `snapshot`，操作资格取 live 订单，不能用快照中旧的订单状态判断现在是否可以操作。
- 中枢界面与 finance 可复用该接口，不需要重新拼装一套取消或版本判断。

## 5. 确认绑定与并发边界

动作捕获 ticket 包含操作者 ID/姓名/角色、原单证引用、完整单证值、原订单引用和订单状态、该单证关联审批值、是否要求编辑模式及已完成标记。确认或 loading 回调执行前，重新计算资格并比较这些值；变化后提示重新核对，不以更改后的内容静默批准。

一个私有的 `documentInFlight` 按单证 ID 互斥，保存的 Promise 排队和导出的定时等待期间也生效。状态更新本身同步完成，第二个提交/审核确认必须重新验证原状态，不能创建重复申请、重复审核或重复修订。成功才反馈，失败不变金额、不变收款、不留错误成功日志。

快照继承继续使用第 2 轮的 `U.inheritDocumentSnapshot`；本轮没有解冻/覆写旧版本。单证动作只回写订单的单证进度，交易明细、币种和收款记录保持不变。

## 6. 实际验证和限制

`node scripts/verify-document-lifecycle.cjs` 使用真实 Promise 和 Node 定时器（把等待压缩至最多 8ms，保留事件循环顺序），通过 **90 组**角色、取消、延迟变化与竞争组合，并补正常流转及资格断言：

- 两取消态直接调用编辑/保存/送审/修订/重制申请/通过/退回/导出，零业务写入；管理员八动作均拒绝。
- 正常提交和审核通过/退回；双送审确认只新增一条；通过/退回两确认竞争只完成一次。
- 五确认动作分别在确认前更改角色、操作者、单证状态、订单状态、最高版本、对象引用、关联订单、制作人，共 40 组原子拒绝。
- 保存的真实 Promise 排队与导出模拟延迟期间变更角色、订单取消态、对象引用或最新版，无额外写入和成功反馈。
- 四业务角色的最新已通过单证可导出演示，跨按钮重复仅一次留痕，反馈明确未生成真实文件。
- 三可编辑状态正常保存且金额/收款不变；保存排队时送审拒绝。历史版八动作、最高版重复、多编号、自审和重复重新制单申请拒绝。
- 正常动作快照不变，金额/收款隔离验证通过。

`node --check` 对 `js/utils.js`、`js/views-docs.js` 和新增脚本已通过。旧脚本的“从旧 V1 再修订成 V3”与复制样例后仍共享原订单/类型最高版等测试前提由中枢按 H10 调整，必须继续保留旧 V1 不变与合法新版本链的覆盖。

本子任务未声称真实浏览器布局、读屏、真实 PDF、服务端权限、数据库事务或多用户并发验证。原生按钮和委托仍沿用现有架构，未引入依赖、持久化、后端或新全局。独立代码评审、真实浏览器、多视角迭代和 GitHub 远端回执由中枢统一追加。

## 7. 复盘

本轮从“纸张不漂移”推进到“这个版本现在是否有权操作”，两者必须分开：历史快照保证旧内容，live 资格保证当前业务状态。最主要收益是取消、旧版和异步确认都走同一规则，用户不会看到隐含的成功或重复审批。

下一步由中枢核查界面按钮、拒绝原因、历史版印章和 live 状态说明的一致性，完成正常主管审核、退回重送、取消冻结及模拟导出的浏览器路径。后续真实系统需要服务端权限、版本唯一约束、幂等键和原子事务；前端互斥只能防本页正常交互，不能替代这些生产保障。

## 8. 补充工作区与销售变更申请专用回归

中枢完成单证工作区/销售入口整合后，新增两个专用脚本。单证 agent 只编写测试和本节说明，未在此补充任务修改运行代码。

### 单证工作区

`node scripts/verify-document-workspace.cjs` 加载真实 `app.js` 全局事件委托、`U.confirm` / `U.openModal` / `U.withLoading` 与单证视图，使用最小 DOM 解析 fixture；没有重写业务动作或用镜像流程代替被测实现。通过：

- 目录只含本订单版本；每项最新/历史标识与当前查看标签正确，一次只标一项当前。
- 主审核动作在来源参考信息之前；真实边界来源文案与原生规则披露保留。
- 有未提交审核意见时点击 `doc-leave` anchor，经真实 app click 委托传递 event 并执行 `preventDefault`，浏览器默认跳转的 fixture 模拟被阻止。取消确认保留原路由、同一个输入节点与文字；确认后才导航，全 MOCK 不变。
- 包装/备注有实际变动时版本切换确认，取消保留字段和当前页面；确认后清编辑状态再导航。原值仅多两端空白不触发假 dirty。
- 装箱单的包装件数实际修改同样触发离开确认；取消后同一输入节点和件数保留，恢复原包装值后正常导航。
- 专注预览仅改变现有布局状态，不重建表单节点、不调用 rerender，审核输入完整保留。

### 销售变更申请

`node scripts/verify-change-request.cjs` 复用同一 DOM fixture，执行实际 `U.openModal` / `U.validate` / `U.withLoading`；**25 组**模态/Promise 回归通过：销售限定入口、禁止订单状态、开窗取消零写入、两个类型的待处理/重复申请拒绝、延迟操作者/订单对象/状态/币种变化时完整 MOCK 不变且不假成功、取消请求记录原 `priorOrderStatus`、不更改旧单证/收款、点击后表单变更不改变已校验申请、双弹窗同类型只提交一次。

有效红灯证据：`node scripts/verify-change-request.cjs --baseline` 只读 `git show ef83c20:trade-doc-demo/js/views-sales.js` 并在隔离 VM 执行，退出码 **1**，首个失败为“改价申请: 已有待处理申请拒绝，完整 MOCK 不变”。本轮修正后普通命令退出码 **0**。baseline 模式不切分支、不修改工作区或 Git 状态，专用于历史缺陷复现。

源码审计发现旧实现只拦截重复取消申请，改价申请未拦截；loading 内重新读 amount/reason 也可能与点击校验不同。已反馈中枢，中枢修正同类型 pending 防御、绑定点击时 Type/Amount/Reason 并复核开窗币种；本子任务按最终源码转绿，不宣称支持所有数值精度/非法金额输入。数量精度与有限数值契约仍留后续。

随后追加严格成功反馈次数断言，发现第二个真实红灯：同按钮连续点击两次，业务申请和日志各一次，但“变更申请已提交”Toast 两次，专用脚本退出码 **1**，`2 !== 1`。原因是成功定时反馈原本在 `U.withLoading` 外，两次 click 都排定时器，之后共用 `submitted=true`。反馈中枢后，成功定时器移入真正首次 commit 的分支，失败和重复点击不再排成功反馈；原断言保留并转绿，确认次数为 **1**。这项修复既防重复反馈，也避免重复关闭弹窗/重绘。

中枢真实 UI 另外发现导出演示留痕成功后时间线未即时重绘，已增加仅成功且当前路由精确为原单证时才 `App.rerender` 的刷新，避免跳到其他页面后被旧导出回调重绘。此问题的实际 UI 复验由中枢浏览器报告提供；本子任务最终重新执行 snapshots、lifecycle、workspace、change-request **四组脚本均通过**（生命周期 90 组，变更申请 25 组）。这只能确认现有 Node 覆盖未回退，不能用来替代时间线的真实布局/点击结论。

两个新脚本语法检查均通过。上述为 Node DOM fixture 的结构、事件与异步逻辑验证，**不是**实际浏览器点击、键盘、焦点布局或截图；真实 UI 覆盖继续以中枢浏览器报告为准。仅对 anchor 默认导航作明确 fixture 模拟，不称测试了浏览器引擎本身。
