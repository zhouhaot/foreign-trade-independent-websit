# 第 2 轮：改价审批先核对再批准

日期：2026-10-07。负责模块：`js/views-fin.js`；专用验证：`scripts/verify-repricing.cjs`。中枢统一整合交接、独立审查、浏览器测评与 GitHub 推送，本说明不代表远端同步回执。

## 1. 缺陷、原因与前后行为

原始样例 `AP20260903` 的订单 `SO2026005` 有 8,000 × 2.60 USD 和 1,500 × 4.90 USD，总计 28,150.00 USD。申请目标为 27,305.50 USD。旧算法先将申请标为已通过，再等比调整且舍入单价，得出 8,000 × 2.52 + 1,500 × 4.75 = **27,285.00 USD**，比目标少 20.50 USD，却仍提示成功并写入日志。

本轮先构造独立候选明细，用整数分核对目标与候选合计。只有相等才修改订单明细、申请审批信息和日志。样例现在保留待处理，原订单、收款、单证、申请审批人/时间/意见、全部业务日志不变；弹窗列出目标、候选和差额，同时说明当前精度与分摊规则不支持该目标。

这一目标确实无法由现有数量和两位单价表达：分为单位时总额是 `8000 × 单价分 + 1500 × 单价分`，必为 500 分的倍数；2,730,550 分不是。因此不能给最后一行单独补差，不能暗改数量，也不能另外保存一个与明细无关的总额。一般情况下本实现只判断当前**等比舍入规则**的候选是否命中目标，不声称已经求解所有可能的两位单价组合。

## 3. 明确假设与撤销方式

- 执行路线中的 H-06：保留数量与现有两位单价，不能命中目标时阻止审批。现阶段只支持当前等比舍入能精确达到的目标，未增加隐藏精度或新调整行。以后获得金额/数量/分摊业务契约后可替换候选算法，仍须保留提交前核对。
- 当前样例使用正整数数量；本轮改价算法限制为正整数数量。销售报价表单数量下限实际为 0.01，因此不能据此断言所有销售表单或订单数量只能为整数。对于小数数量，改价明确拒绝并解释当前算法限制；确认分数数量和行金额舍入规则后再扩展。这是本轮支持范围的限制，不是已确认的全系统数量契约。
- 关联收款币种不一致视为待纠正数据，不能折算或跨币种汇总。若未来支持兑换收款，必须在后端契约中明确汇率、结算币种与凭证。
- 低于已收目标涉及退款，当前没有确认规则，因此拒绝。不得通过自动增加退款记录来使审批通过。
- 重新制单是明确采用当前交易信息的新版本动作；包装/备注受控修订沿用旧交易快照，由单证负责人实现。弹窗说明快照来源，原版不变。
- 写操作仍只修改内存，刷新恢复样例；前端权限和同步回调不代表服务器鉴权或数据库事务。

## 5. 复盘与下一步

本轮收益是阻止错误财务状态，而不是提高改价成功率。20.50 USD 的差额不再隐藏在成功提示后。对两位单价无法表达的金额先给出解释，避免以修改数量或独立总额制造假勾稽。

下一步明确数量/单价/行金额/目标金额和分摊契约，再决定是否采用精确十进制或提高显示与保存精度；验证目标可表达性要与等比规则的可实现性区分。生产系统还需要服务端重复请求、并发审批、权限和数据库事务，本轮未实施。
