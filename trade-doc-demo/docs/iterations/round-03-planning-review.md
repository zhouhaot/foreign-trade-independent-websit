# 第 3 轮现实规划复核：单证审核作业区与当前资格

日期：2026-10-07。开工基线：`ef83c2051dea68ae25bafb46f1f15479abff4268`。本文件只给可落地的规划契约和验收目标；执行结果以中枢的当轮报告、独立审查与实际测试证据为准。

## 目标与现状证据

本轮让员工先识别“当前在看哪个版本、订单是否仍执行、有什么下一步”，再执行单证工作。沿用 A 配色和三块作业区，不重新选视觉方向，也不扩大单证类型。

规划已读 `AGENTS.md`、`HANDOFF.md`、`PRODUCT.md`、第 2 轮复盘与路线，并核对 `js/views-docs.js`、`js/views-fin.js`、`js/views-sales.js` 的实际动作。发现：

| 问题 | 开工代码证据 | 影响 |
|---|---|---|
| 资格只按单证状态判断 | `rightPanel`/`doc-export` 只查 `d.status === 已通过` | 已取消订单、存在新退回版的旧通过版仍能演示导出 |
| 使用历史订单快照展示操作 | `Views.docDetail` 的 `order = snapshot.order` | 不能把冻结订单当实时取消状态；旧纸张不应随取消而改写 |
| 入口与延迟确认缺少统一校验 | `doc-submit`/`doAudit`/`doc-reform` 没有完整角色、最新版本、订单和同操作者复查 | 隐藏按钮不足以阻止直接调用，开窗后变化可能作用于未展示对象 |
| 取消提示与实现不同 | `ap-handle` 写关联单证作废，`applyApprovalEffect` 仅改订单状态 | 把暂停当前使用与历史版本已作废混为一谈 |
| 历史与当前版本未区别 | 历史已通过横幅写本版本可导出，审核章始终显示 | 员工可能把曾经通过理解为当前版本有效 |

以上是静态代码检查，不构成真实浏览器、生产安全或历史签发验证。

## 显式假设与状态契约

H-09：取消申请中与已取消订单暂停单证写操作和导出演示，但保留历史查看。H-10：当前业务资格给同订单同类型唯一最新版本，且审核通过才可演示导出。H-11：导出演示沿用现有业务查看角色，不增加管理员业务权或改变未确认的跨业务员记录范围。

这三项是缺少真实流程输入时的保守、可撤销原型策略，用户尚未确认企业凭证作废、版本生效、退款或恢复订单的正式规则。未来若允许历史副本导出，应作为明确新用途与文案，并经新的业务契约实施；本轮不偷偷增加该路径。

| 实时订单/版本 | 查看纸张与审核留痕 | 单证员动作 | 主管动作 | 导出演示 |
|---|---|---|---|---|
| 正常订单，唯一最新草稿/制作中/已退回 | 可按原角色读取；退回意见常显 | 编辑允许字段、保存、送审；已退回可申请重新制单 | 不能审核非待审核版本 | 不可，明确尚未审核通过 |
| 正常订单，唯一最新待审核 | 可 | 不可再编辑/重复送审 | 同主管账号且非自制可审核或填写意见退回 | 不可，明确待审核 |
| 正常订单，唯一最新已通过 | 可，展示当前资格 | 受控修订生成下一个版本，原版保留 | 无需再次审核 | 原可读业务角色可演示；明确不生成真实PDF |
| 正常订单，旧版本（包括旧已通过） | 可；显示历史版本及最新版本入口 | 不编辑、不从旧版本重复派生新链 | 不再审旧版本 | 不可，说明当前最新版本与其状态 |
| 取消申请中或已取消订单，任意版本 | 可；保留实际历史状态与快照 | 写操作/修订/重新制单暂停或终止 | 单证审核暂停或终止 | 不可，原因优先显示实时订单状态 |
| 实时订单/版本缺失，类型或最高版本冲突 | 已有完整快照可保留只读历史；不能偷读当前主数据补纸张 | 拒绝 | 拒绝 | 拒绝，给具体缺失/冲突信息 |

最新版本按现有订单和 CI/PL 类型链理解；现有编号作为链标识一并检查。若一个订单同类型出现多编号而无法判定唯一链，或重复最大版本，不按时间、数组位置或新编号猜优先级，应阻止业务动作并显示冲突。对旧版不把 `status` 改为“已作废”，不删除审核章、审批人、快照或历史；章与横幅使用“该版本曾审核通过”等历史语义，当前使用资格置于纸张外作业区。

取消申请拒绝后可恢复当前既有执行中路径，但现有 Mock 没有前置订单状态，不应捏造“已精确恢复原状态”。如果实现增加新申请前状态，仅对新增内存申请记录真实捕获值；旧样例缺失值应标明现有回退策略。退款、收款核销、已签发外部文件撤回、恢复已取消订单均不在本轮。

## 实施片段与文件所有权

1. **单证动作与资格**（`js/views-docs.js`；共享方法若需要由中枢指定 `js/utils.js` 单写负责人；复杂度中、风险高）。统一资格结果用于按钮、原因、入口与提交再校验，避免 UI 与动作各维护一套规则。对象须仍在当前集合且身份一致；跨角色/会话、实时取消、版本变化、重复提交均原子拒绝。等待中只允许一项动作生效；快照捕获/继承失败不能留下新版本或先批准。
2. **取消与重新制单相邻契约**（`js/views-fin.js`；复杂度中、风险高；依赖步骤1资格定义）。取消确认清楚写暂停业务和保留历史；不批量改历史审核结果。重新制单申请只从最新退回版、正常订单发起，主管审批提交时再次验证；取消后已有申请保留待处理事实但无继续操作资格。取消申请本身仍可按主管权限处理，不被单证冻结误拦。
3. **作业区信息层级**（`js/views-docs.js` 与中枢负责的 `css/pages.css`；复杂度中、风险中；依赖契约）。版本与订单状态、当前资格、退回意见、主要动作常显；时间线与完整规则渐进披露。1280下纸张可读，审核/送审动作不会被低频规则挤出常见1000高视口。不为挤首屏缩小正文字号或删除真实交易字段。
4. **验证与独立复审**（`scripts/verify-*.cjs`、`.impeccable/review/round-03/`；复杂度中；依赖步骤1～3）。先记录可复现失败再修复，保留第2轮8组回归；至少两轮岗位/业务/视觉/键盘评测并记录修正。中枢统一改 `HANDOFF.md`、总体报告和Git，本文只维护规划。

所有实现延续普通脚本、全局动作委托、内存写入与刷新复位；不引入真实后台、依赖、持久化或批量样例改写。

## 验收矩阵与证据要求

- 取消前的已通过、待审核、已退回、草稿分别测试；取消申请中及批准后，从按钮与直接动作均不能修改/送审/审核/派生/导出。订单取消保持收款金额、单证快照和既有审核历史；只有本轮明确预期日志变化。
- V1已通过→V2草稿/退回/待审核时，V1纸张与历史不变、当前资格关闭；V2通过后仅V2资格开放。不能用旧版本审批记录满足新版本；修订和重新制单不得并发产生重复版本。
- 开确认框后更换身份、版本替换/删除、新版插入、订单取消、申请变化、对象有效到另一有效值、重复点击/双弹窗均应拒绝未展示数据；失败不得先改状态、审批人、历史或金额。
- 单证员、主管、业务员、财务、管理员分别核对页面和直接动作：只读角色不修改，管理员不业务审批/导出，主管自制自审拒绝，退回意见为空不能退回。
- 真实UI完成一条最新版送审→主管退回→单证员修改重送→通过→导出演示路径；另一条取消后只读路径；历史与当前版切换时对象/版本/资格可理解。实际浏览器工具限制内，通过UI驱动业务，不绕过策略注入状态。
- 1280/1440真实尺寸截图与DOM位置、控制台、键盘Tab/原生披露/弹窗焦点回返；状态同时有文字，退回原因不依赖颜色。截图须对应修正后版本；若未执行file://、跨浏览器、打印、读屏，分别记未验证。
- Node测试可以构造状态排列与并发桩，但不能替代实际布局/浏览器。审查报告区别“规划验收目标”“已运行通过”“未覆盖”；推送只能在独立代码和设计复审后由中枢做，并回读远端SHA。

## 风险与现实收益

最大风险是用前端历史状态代表正式单据效力。将实时资格与历史事实分开，在取消/旧版页面写具体原因，可直接降低员工误操作且不破坏第2轮冻结成果。其次是重复版本与异步期间漂移：在入口和提交时按同一规则校验、绑定操作者/对象及共享锁，比只隐藏按钮更接近以后服务端契约；当前仍无法替代真实服务端授权、持久事务或审计。

本轮交付判断以可操作结果为准：员工能辨认版本和阻断原因、完成合法下一步、旧事实保持不变；不是以更改颜色、提交数量或把待处理状态批量清空来显示进展。下一轮优先岗位上下文连续性或报价/收款有限数字与精度提示，依本轮复盘实际问题调整。
