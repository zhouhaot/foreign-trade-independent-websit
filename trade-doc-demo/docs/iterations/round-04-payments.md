# 第 4 轮：收款登记与余额核对

状态：实现与隔离契约验证通过，等待中枢浏览器测评、独立代码复审与本轮封版；以本轮总报告为准。

## 问题与目标

旧登记从订单下拉选项的 `data-out` 读取可收上限，延迟回调再读取当前表单值。两处读取之间，订单、余额、币种、登录人员或表单内容可以变化；固定时间成功提示也未绑定实际写入结果。通用数字校验没有限定有限普通十进制和最多两位小数。汇总还通过 `Math.max` 把负余额显示为零，且直接合计关联订单的所有币种。

本轮只修静态原型中的本地登记与显示契约：财务登记时核对实时对象、状态、同币种余额和输入精度；成功记录与日志使用同一次已核对的内容；失败保留输入并说明具体字段和完整原因。主管继续只读，历史记录保持可见。

## 假设与边界

- H13：订单处于「取消申请中」或「已取消」时暂停新增收款；历史收款保留。本轮没有退款功能，也不把暂停等同于已退款。
- 收款金额至少 0.01、最多两位小数，且能安全表示为整数分；不接受科学计数法、非有限值或通过舍入修正过精度输入。
- 收款日期必须是真实日历日期；没有已确认的未来日期禁令，因此未来日期仍可登记。
- 本轮继续只改内存；没有服务器事务、真实身份验证、汇率或持久化。延迟和重复守卫验证的是原型行为。

## 改进清单与验证

| 改进 | 实现前 → 实现后 | 验证依据 |
| --- | --- | --- |
| 财务动作权限 | 只隐藏表单 → 原生提交入口与延迟回调均重查财务身份，同账号姓名与 ID | 四类非财务角色、延迟角色/操作者变化零写入 |
| 实时订单资格 | 缓存选项金额 → 实时订单同一对象、支持的状态、启用币种与同币种余额；取消两态暂停新增 | 缺订单、订单替换、币种、状态、明细、客户、缓存上限和字典停用 |
| 无损金额 | 通用数字转型 → `U.decimalInput` 验证普通有限十进制、最多两位、最少 0.01、安全整数分及可无损保存 | 0.001 / 1.005 / Infinity / 指数 / 十六进制 / 超范围被拒绝，保留原输入 |
| 表单内容绑定 | 延迟时读取新输入 → 捕获已核对全部输入；延迟时逐字段比较，发生变化要求核对后重新提交 | 金额、币种、方式、日期、备注和订单 valid A → valid B 均不得悄悄写入 |
| 实时余额重查 | 选项显示金额作上限 → `U.financialBalance` 重算；其他收款变化即使余额仍够，也要求重新核对 | 同单新增收款导致剩余 2,100 时，原 10,000 提交失败；修成 2,100 后恰好结清 |
| 方式与日期 | 仅日期必填 → 当前启用收款方式标签 + 原有「其他」，真实日历日期 | 禁用方式/代码值/无效日历日期拒绝；未来日期与有效闰日接受 |
| 重复与并发守卫 | 仅按钮 loading → 同订单锁 + 成功表单记忆；旧表单/新表单替换均失效，失败释放锁 | 同次双 submit、旧成功表单再提交、两表单替换与失败后重新提交 |
| 成败反馈 | 固定 480ms 成功提示 → 实际写入后才提示成功/重绘；失败字段错误、完整 inline alert、简短 Toast 且保留输入 | 零写入、无假成功、失败无重绘、`aria-invalid` 指定字段 |
| 应收异常可见 | 混币种合计/负余额隐藏 → 共享余额核对；异常行显示红色文字原因，不画正常结清条 | 异币种与超收拒绝新增，历史记录保留且可查 |
| 客户币种汇总 | 浮点累计 → 同币种整数分累计；异常订单排除且显示数量；合计超安全范围显示异常 | 同币种 USD/EUR 分开，异常排除提示，不猜测无效金额 |
| 失效预选与孤立历史 | 失效预选默认换成另一单/缺关联订单抛错 → 原选择不可登记提示并保持空选择，缺订单的历史记录显示明确占位 | SO2026006 原选择失效、记录关联订单删除后视图仍能渲染 |

文件：`js/views-fin.js` 仅收款与应收区；新增 `scripts/verify-payments-contract.cjs`。共享数值、币种、日历和余额工具由中枢维护于 `js/utils.js`，此实现使用约定 API，没有另造一套舍入逻辑。审批改价、取消与重新制单区没有改动。

实际隔离验证：专用脚本 67 场景 PASS，使用真实 `U.withLoading`、Promise、短真实定时器和原生 submit/change 监听器。失败前后比对完整 MOCK，成功比对只新增一条收款与一条订单日志，订单明细/状态与全部单证快照不变。特别补测订单 ID 属性变更失败后释放原订单锁，再次核对可登记。`verify-repricing.cjs`、`verify-cancellation.cjs`、`verify-document-snapshots.cjs` PASS；两个所属 JS 文件 `node --check` 与所属差异 `git diff --check` PASS。

相邻脚本 `verify-views.cjs` 的 100 个角色/视图渲染通过，但其后报价生成订单动作因另一模块新增 `modal-root` 访问与旧测试 DOM 桩不匹配而失败；已交中枢/销售实现 agent 更新测试桩，未将该动作算作通过。本材料不替代中枢的最终统一结果。

## 本次复盘

把错误保留在表单附近，使财务人员能看清为什么没有登记；将账户、表单、交易和余额分别绑定，则不能依赖隐藏按钮或旧选项建立写入资格。失败不更新原记录，不清空需要修正的输入。未来日期禁令、退款与服务器事务都没有明确业务依据或现有服务，所以本轮只记录边界，不添加无法验证的规则。
