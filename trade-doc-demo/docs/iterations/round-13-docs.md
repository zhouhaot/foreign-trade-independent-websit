## 逐项改进

### 1. 草稿／制作中的编辑提示对应当前实际身份

前：所有进入该 View 的岗位都看到“字段可编辑”，包括业务员、财务和主管。后：仅 `policy.canEdit` 为真显示编辑指导；其余显示“当前只读”与原 `policy.reasons.edit` 全文。历史旧版、取消申请中、已取消、版本冲突、缺关联订单或缺有效身份均沿原原因说明，不按岗位名猜资格，不短截原因。

验证：实际样例五角色、草稿主管、历史版本、真实取消／恢复流程、隔离异常及 `ctx.user` 与 `App.user` 故意不同的专用场景。最后一例仅核横幅使用 actual ctx，不改变原右栏实现或扩展新身份契约。

### 2. CI 与 PL 的可编辑字段指导对应本类表单

前：CI 也承诺可编辑包装，实际 CI 表单没有包装控件。后：可编辑 CI 仅提示“唛头与备注字段”；可编辑 PL 保留“唛头、包装与备注字段”。订单带入客户、商品、金额只读的原事实句保留，未改预览工具栏、纸张或输入控件。

验证：真实 CI 制作中和隔离 CI／PL 草稿候选。状态候选仅在 Node fixture 中准备，不用于伪造实际样例截图或称真实业务创建。

### 3. 退回记录保留，重送指导取当前资格

前：只要当前角色为单证员，所有已退回版本都指导修订重送，历史 CI2026003 V1 也如此。后：原退回意见、处理姓名、处理日期及标点事实前缀逐字保留；仅 `canEdit && canSubmit` 为真指导按意见修订后重新提交，其余显示完整 edit 阻断原因。原历史意见不会因新指导而被覆盖，也不承诺当前旧版可修订、送审或重制。

验证：原历史 CI、真实当前 PL、五岗位、真实取消申请／取消通过状态；原意见／姓名／日期带 HTML 字符的隔离反例确认转义与完整事实前缀。这里“修订后重送”是原已退回版本编辑送审路径，未调用或改变已通过单证生成新版本的受控修订 Action。

### 4. 重制申请指导不忽略原待处理申请

前：PL2026004 V1 原横幅一律提示可申请重制，原审批中已有待处理重制申请，按钮和 policy 已拒绝重复。后：当前可修订重送时仍给主路径；仅 `canReform` 为真补“也可申请重新制单生成新版本”，否则显示原完整 `reasons.reform`。真实 PL4 因待处理申请而显示请勿重复提交，不改申请或审批状态。

验证：真实样例 PL4 的 pending 原因与按钮状态；另在隔离 Node fixture 删除该 pending 候选验证原 policy 实际允许 reform 时才显示申请路径。隔离准备不是改变源 Mock，也不是声称样例已处理该申请。

### 5. 两分支以外的事实、页面与动作保持原行为

已通过、待审核、未知三横幅分支原 HTML 精确保留；待审核继续只表达原提交事实与等待主管处理，没有加入新的可审核承诺。`rightPanel`、预览工具栏、H19 审核纸张、版本目录、来源说明、审核留痕、全部 Actions 和资格 helper 未改。横幅只纯读内存，不改金额、收款、单证 status／history／snapshot。

验证：在同一个实际 fixture／同一冻结时间与快照中分别调用固定基线和当前 View，去除横幅后整页 HTML 必须精确相等；源码去除仅两个拥有的分支行后全文（只统一 CRLF／LF）必须与基线相等。通过／待审核／未知分支自身另逐字比较。真实取消申请、主管退回恢复和主管批准取消后，单证全数组（含历史及快照）均保持原值；View／原拒绝编辑 Action 的完整 MOCK 无写另检查。
