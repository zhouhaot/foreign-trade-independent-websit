## 已复现的两个缺陷

1. 原 `Number(value) || value` 把 `1e3` 箱数静默写成 1000，`0x10` 等非普通数值表示也可被接受。新脚本在实现前首个红灯退出码 1：“指数箱数必须拒绝，不能被 Number fallback 保存为 1000”。
2. 不进入编辑直接送审时，原流程只看角色/版本/订单资格，不校验存储中的包装。隔离 VM 以 `--baseline-readonly` 只读加载 `cff1a0e` 的原单证代码，给样例 PL 箱数 `bad` 后直接送审，退出码 1：“原非编辑送审跳过 storedPL 校验，非法箱数被送审”。未修改 Git 状态或原 Mock 源码。

## H18 范围和可撤销规则

H18 是本轮显式原型假设，只作用于 **PL 装箱单**。草稿允许部分空白待补，已填写值仍全部合法；送审必须五字段完整且符合正数规则。CI 商业发票不受隐藏包装字段门槛，保存或送审也不修改隐藏包装。

箱数为普通十进制正安全整数；重量显式 KG/KGS，体积显式 CBM，度量允许普通小数或标准千分逗号、最多 3 位小数，精确缩放后不超过安全整数范围。毛重不能小于净重，可相等。未填不自动变 0，不接收指数、十六进制、NaN/Infinity、负零/负值、非法逗号分组、缺单位或超精度。包装方式要有可见内容，多语言/emoji 合法文字不自动洗值。具体解析、纯候选与边界 oracle 由中枢的包装契约脚本独立覆盖。

这是输入契约，不证明实际测量正确、运输包装合理、每行货物已匹配或真实业务制度确认。以后支持其他单位/字段精度需调整明确契约和测试，不能隐式转换原包装文本或重写历史版本。

## 原子边界与共享接口集成

保存使用 `U.packagingCandidate(raw, {requireComplete:false})`，送审使用 `true`。失败返回 `packing=null` 不读取部分结果。原 marks/remark、包装、更新时间、history、审批列表、订单单证进度均不改变；不调 markDraftClean、不 rerender，DOM 与 dirty 输入保留。只有候选和原票据都通过才一起应用候选并留痕，成功后再 clean。

readonly PL 送审也以存储 `d.packing` 生成完整候选；空/无效包装对象不被合并成空对象而“洗白”。CI 的包装字段不收集、不解析、不应用。单证原角色、取消两态、最新版、对象/状态、关联审批及互斥条件保留，新增同值替换的 actor 对象、源页面、原编辑节点/内容检查。

失败显示具体字段及原因，Toast 只作短反馈，完整原因在右栏。对合法 B 漂移提示核对当前内容后重新保存/送审；非法 B 漂移同时展示当前字段的具体诊断。候选保留现有 KGS/CBM 原文，不自动转换计量单位。

## UI 和样式交接

- 包装字段：`.packing-field`，对应 label 与 `df-pk-KEY-hint` / `df-pk-KEY-error`；没有在允许空白的草稿永久标 aria-required。
- 右栏完整错误：`#doc-packing-feedback.packing-feedback`，`role=alert`、`tabindex=-1`；非编辑送审失败可聚焦完整原因后通过既有“编辑包装与备注”接续。
- 只读空白：`.packing-pending` “待补”；保存完整性：`.packing-readiness`。文案明确来自已保存模型，不以实时 rerender 伪装成输入动态校验。
- 错误和 hint 的字号/换行/两宽布局由中枢 CSS 单写与实测；本子任务未改 CSS，未声称截图通过。
