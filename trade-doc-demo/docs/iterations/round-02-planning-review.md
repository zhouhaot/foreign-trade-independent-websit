## H-06：通过的是当前等比候选，不是全部可能组合

`prepareRepricing` 先读数据、校验正整数数量、两位正单价、目标安全整数分、收款金额和同币种，再构造独立候选。仅候选合计等于目标且不低于已收才提交；失败不会先写申请状态、审批人/时间/意见、订单、单证、收款或日志。延迟回调再次校验，避免“弹窗打开时合法，提交时已变化”。

具体缺陷样例 AP20260903 / SO2026005：目标 27,305.50 USD，等比两位舍入候选 27,285.00 USD，差 20.50 USD。固定数量 8,000 和 1,500、单价按分计时，总额必须是 500 分的倍数；目标 2,730,550 分不满足，所以这个样例在当前精度下确实无解。

这个特例的数学结论不能泛化为整个求解器。本实现只检查一组等比舍入候选；有些目标可由其它单价组合表达，但不被当前候选命中。此时正确解释是“当前等比两位分摊方案未命中”，而不是“任何两位单价都无法实现”。后续改价成功率的提升要在精度、数量与分摊业务契约确定后开展，不暗改数量或插入独立调整总额。

### 材料需修正的边界

worker 材料称“当前样例和销售表单使用正整数数量”。样例数量确为整数，但实际 `views-sales.js` 报价保存只设置 `number/min:0.01`，并没有整数校验。建议文字改为“本轮改价支持正整数数量；报价输入当前允许小数，相关精度契约未定”。不因材料不准确而自行收紧报价业务范围。

当前报价/收款一般表单的有限数字与精度规则没有因此全量修复；改价专用校验通过不能传播为“所有数字输入已安全”。这是第 3 轮可选的具体表单工作，不在本复核扩大改动。

## H-07：冻结的是本次样例基线，两个新版来源明确

`U.captureDocumentSnapshot` 深拷贝 seller、customer、完整 order 与每行 product，递归冻结且锁定版本 `snapshot` 属性。CI/PL 和单证台账客户取已有快照，缺快照明确报错，不回退 live 主数据。

两个创建路径准确分离：

| 路径 | 实际交易来源 | 原版本 | 必须保留的说明 |
|---|---|---|---|
| 初始化现有演示版本 | 页面加载时当前 Mock，`basis=demo-baseline` | 本次加载建立基线 | 没有当时签发记录，不称历史恢复；冻结时间与原样例日期不同 |
| 包装/备注受控修订 | 原版本快照内容/来源/冻结时间，独立深拷贝 | 不变 | 只修唛头、包装与备注；不借此吸收新的价格或客户 |
| 审批重新制单 | 当前订单/客户/商品/卖方，`basis=creation` | 不变 | 批准前捕获；失败不批准；原包装被复制，需要制单人核对是否仍适配新交易 |

界面已明示交易冻结、样例基线不能还原历史及修订来源。保留这个说明是为帮助用户判断版本依据；下一轮可调整信息层级，不能在视觉精修时删除事实边界。

尚未实现真实历史数据、永久保存、审计签名、多人并发版本分配、服务器权限或真实 PDF。`Object.freeze` 防误改不等于防篡改认证，重新加载时消失的新增版本也不能当作档案。

## UI：已进步的语义与终审关注项

无单证不再把“未开始”画成完成勾；列表/详情共享最新版本阶段；全体通过后第四节点明确为“可导出”资格，没有冒称已实际导出。公共局部间距调整的方向也正确：缩留白、保留字号与点击尺寸。

需中枢和设计 reviewer 继续核对：

1. `documentStages` 当前把“已退回”计入 sent。如果两类最新单证都退回，制作/送审会同时画完成勾。说明应区分“曾送审”与“修订后已重送”，避免阶段图传达错误的下一步；现有测试只覆盖制作+退回组合。
2. 订单汇总标签与最新单证集合不一致时，保留真实标签但不要让四阶段看起来是已核实的整体完成；未知状态需明确“阶段需核对”。本次测试没有覆盖所有这种组合。
3. 阶段颜色、数字或图标仍须有对应文字状态；本轮 Node 对 HTML 的断言不能证明读屏可理解。主动作是否回到首屏，应回读实际视口、滚动和按钮位置，不凭 CSS padding 宣告达标。
4. 数据来源信息增多后，检查 1280px 纸张阅读、退回意见和动作是否互相挤压；低频细节可以渐进展开，来源/版本和异常必须保持清楚。

这些是实际差异对应的终审检查点，不代表我已观察到真实浏览器缺陷；修正及复测结果应由中枢追加到最终轮次说明。

推荐 A。原因是第 2 轮新加入真实的快照来源和修订含义，单证区的信息层级马上影响操作者理解和下一步动作；这是有明确新信息压力的 UI 打磨，沿用已有审批与编辑路径即可交付，不需要硬件、后端或新业务规则。若第 2 轮终审发现阻断，先修阻断再进入候选。
