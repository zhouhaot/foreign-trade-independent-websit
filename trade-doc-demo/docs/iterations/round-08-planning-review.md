## 已核实问题与现实收益

推荐UI为主的小交付：将CI/PL纸张底部的当前审核表达与历史决定分开。员工只看纸张时，也能辨认该版本是否通过，而不会把上次退回人误认成批准人。保留交易快照、历史审核事实、退回意见及最新版本/当前导出资格，不增加正式签名、PDF或后台能力。

真实代码两种纸张均无条件输出`审核 Approved by：d.approver || 待审核`（核查时`views-docs.js:275`/`324`）。`doAudit`通过或退回都把处理人写入`approver`/`approvedAt`；重新送审只改status/submittedAt并追加历史，不清上次决定。保留历史本身正确，但将历史处理人直接填进Approved by语义不准确。

## H-19：可撤销的前端审核表达假设

H-19建议：只有当前查看版本的`status === 已通过`才在纸张Approved by位置显示该版本的审核通过记录姓名。草稿/制作中显示尚未送审，待审核显示等待本次审核，已退回显示未通过/已退回；历史退回处理人留在历史/退回说明中，不能替代本次批准人。

这解释的是Demo数据中的审核状态，不推断真实授权签署、签发、外部撤回或法律制度。系统当前仅有演示审核数据，没有电子签名、签名图像或正式签署记录；即使审核通过，也不据此宣称已正式签字。模板签字栏可保留，但如需补文字，应写演示签字栏等准确范围，不虚构实际已签署或未签署事实。

| 当前查看版本 | 建议纸张表达 | 历史与当前资格 |
|---|---|---|
| 草稿/制作中 | 审核状态：未送审 / Not submitted；不填批准人姓名 | 既有历史原样，尚无本次通过 |
| 待审核（首次） | 审核状态：待审核 / Pending review；不填批准人姓名 | 送审时间与当前状态不变 |
| 待审核（退回后重送） | 等待本次审核；不以旧approver填Approved by | 上次退回人/日期/意见作为历史决定保留 |
| 已退回 | 审核状态：已退回、未通过 / Returned, not approved | 退回意见与处理人可在现有说明/留痕读取 |
| 已通过且有有效姓名 | Approved by显示该版本通过记录 | 原通过姓名/日期/章/交易内容保留；不暗示正式签字 |
| 已通过但无可见姓名 | 已通过；审核人记录待核对，不凭空补人或改成待审核 | 原已通过事实与章保留，当前导出资格独立 |
| 已通过，有姓名但缺日期 | 保姓名；审核日期待核对，不猜日期 | 原数据不写，签字模板与当前资格不因显示改变 |
| 旧已通过版本/取消订单的通过版本 | 仍显示该版本真实通过记录 | 当前操作区继续历史只读/暂停导出；不能靠抹历史表示无当前资格 |
| 未知状态 | 状态待核对，不默认Approved by或已通过 | 不自修状态或猜正式决定 |

姓名字段须维持转义；已通过纸张的交易字段与现有审核片段尽量原样，不为统一样式洗历史。若增加“上次退回决定”短上下文，必须从可验证历史决定标为过去，不能把当前待审核说成当前已退回。材料不得将这项显示修正称清理审批数据。

撤销方式：企业后续明确纸张审核栏与正式签字栏关系、重送/历史批准记录和签发规则后，再调整展示及回归；不得回写旧快照或删除旧版本。当前不借UI契约推翻H-09～H-18。
