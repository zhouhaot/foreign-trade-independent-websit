## 员工主任务与信息层级

主管核对待办后按现规则处理；业务员/单证员阅读本人申请结果并查看关联作业。主任务不改为操作历史申请，不增加筛选/队列/SLA/双栏sidebar。原待处理6列、已处理8列均保；6/8是列数，不是记录数。按当前样例原counts：主管5待处理/3已处理、业务员陈明2/2、单证员王芳3/1、财务赵倩0/0；管理员原路由拒权。原排序/次数、申请人与处理人/两时间/状态/意见不可为容纳新上下文而删掉。

建议事项栏内部有序排：原事项正文 → 申请编号AP与真实关联对象/版本 → 原申请理由。事项仍首层，不用细灰字承担全部识别；申请编号便于区分同订单多次申请，关联对象便于确定查看去哪。主管原“处理”是主要动作，新增查看作次级链接；其它岗位仍等待主管或阅读结果，无新增审批按钮。原申请原因与处理意见不同，分别具名，不能用历史结果tag替代完整意见或把新关联对象当申请原目标金额。

已处理较长理由可用原生details后置展开，summary具名“原申请理由 · AP编号”，内部保原文；原处理意见留现列全文自然折行。短理由可直接显示。空理由/意见沿既有占位或“未记录”，不补实际客户需求、日期/批准人或金额。长文本折行而非title/tooltip/省略号唯一承载，英文编号也可在必要处自然换行；不能缩字号裁掉原因。实际1280若仍拥挤，先根据首图局部限制日期/人员/操作宽度并给事项/意见足宽，再决定最小修正，不预造多套布局。
