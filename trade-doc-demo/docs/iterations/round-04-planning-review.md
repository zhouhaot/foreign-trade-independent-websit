# 第4轮现实规划复核：报价与收款的输入及提交契约

日期2026-10-07，基线`2414905939c4c3dd275912c95d9af11f8f729952`。第3轮已完成并保存验证、复审、实现与回执推送记录；本轮实施进行中。本文是可执行规划与开工红灯证据，不能当作第4轮已通过报告。

## 需求与开工证据

让业务员能看懂报价输入精度、确认有效报价并仅生成一次订单；让财务按当前订单币种与真实未收登记，不以缓存值或已失效身份写入。保留现有销售主流程、分币种、单证与收款并行、内存写入和A视觉。

| 现存问题 | 基线位置 | 后果与优先级 |
|---|---|---|
| 数字校验只有isNaN与上下限 | `js/utils.js:294`～`309`，关键302～305 | Infinity能进入无max报价字段；数字表达和精度未界定。高 |
| 无效预览当0，保存直接Number写对象 | `js/views-sales.js:281`～`320` | 非法输入显示貌似正常金额，保存缺完整候选/提交角色与状态重查。高 |
| 报价确认与生成只部分检查状态 | `js/views-sales.js:180`～`239` | 假身份变化、直接调用、有效内容漂移和双弹窗缺完整绑定。高 |
| 收款上限读option缓存，异步重读表单 | `js/views-fin.js:231`～`254` | 正常等待中更换对象或余额降低仍可能登记；财务身份、取消、币种没有提交时完整检查。高 |
| 已收不校验币种，未收钳制为0 | `js/utils.js:130`～`145` | 异币种被同数计入，负余额变正常结清。高 |

只读Node VM加载真实mock-data/utils、对U.validate数字规则及内存金额方法实测（未写文件、未改原Mock源码）：`Infinity`、`1e309`、`0x10`、`1e3`、`1.001`均被当前报价数量校验接受；`0.01`也接受。向USD的SO2026001隔离副本增加1EUR，received增加1；再构造超收，actualBalance=-12001，reportedOutstanding=0，status=已结清。前四种是普通十进制契约的拒绝项，1.001是拟定两位精度拒绝项，不把拟定规则伪装成原有制度。

这份红灯证明代码现状，不证明真实浏览器、财务业务或服务端事务结果。具体动作回归由实现worker建立并保存红→绿记录。

## 明确假设与最小规则

H-12：本轮报价数量、单价和收款金额采用普通十进制最多两位小数，至少0.01；保留数量0.01。每行数量×单价必须精确到分，再以整数分合计，不做隐含舍入、增减数量或调整行。0.01×1.00可用；0.01×0.01低于分精度，明确拒绝；0.10×0.10为0.01，应可用。若实际业务需更高数量/单价精度或行舍入，另行收敛正式规则。

H-13：取消申请中暂停新增收款，已取消禁止新增收款；旧记录和金额保留。这是独立财务原型假设，不能仅引用H-09单证暂停推断已有制度。当前不生成退款、核销、汇率差或恢复取消订单流程。

- 解析允许首尾空格，拒绝空值、非有限值、指数/十六进制、千分隔符、正负号混用、超精度及安全范围外数。候选的缩放整数、每行乘积、总额与收款累加均检查安全范围；不能先Number导致精度丢失后再假装验证原输入。
- 先验完整候选后一次性改内存；失败保持报价/订单/收款/申请/单证/日志不发生部分更新，成功反馈只在实际提交后产生。日期验证真实公历值；无事实依据不增加未来日期或报价到期的业务禁令。
- 当前报价UI只有USD/EUR；mock字典中两项启用，CNY禁用。共享helper与选择器应核对现有启用项，不接受伪造未知/禁用币种，也不将两位精度推广到未知所有币种。客户和商品关联必须真实存在于当前样例对象；不存在不能以空名/0单价继续确认生成。
- 报价保存、客户确认、生成订单仅sales；财务登记仅fin，主管仍只读；不改变未确认跨业务员记录范围。入口、确认及延迟提交绑定同账号会话、对象身份和业务内容，不能把合法内容A改成合法B后批准未经展示的B。
- 收款余额来自当前订单明细及全部关联同币种有效记录。返回明确错误或`totalCents/receivedCents/balanceCents/overpaidCents`等可核对值；异币种/非法记录不静默过滤，超收保留负余额/超收原因并禁止继续登记。正常未收视觉可用非负值，但必须同时显示异常，不把超收称正常结清。
- 不全局重写U.validate默认行为以破坏其它表单；新helper或可选严格规则服务本轮入口。第2轮改价目前只支持整数数量，H-12不自动放宽该算法；旧版单证交易快照不改写。

## 红灯到绿灯验收矩阵

| 范围 | 失败/漂移场景 | 成功边界与不变项 |
|---|---|---|
| 解析与候选 | Infinity/NaN/1e309/指数/hex/空/负/0/超2位/超范围；每行不足分或总额溢出 | 0.01数量与合法两位输入、小数精确行金额；不改数量凑账、不隐含舍入 |
| 报价保存 | 非sales、已确认、route与表单quoteId不同、失效对象/商品/客户、未知币种、任一行非法 | 所有字段一次提交，合计对应可见明细、币种联动；失败原报价不变且字段错误具名 |
| 确认/生成订单 | 开窗后角色/会话/对象替换、内容A→有效B、客户/商品变失效、重复确认/双弹窗、已生成 | 仅已确认报价且无orderId生成一次；关联日志一次、明细独立副本、旧单证不变 |
| 收款输入 | 0.001/1.005/非有限/超范围/金额超过余额、伪造方式/日期/币种、异币种或非法既有记录、超收 | USD/EUR各自成功、恰好结清、两位整数分合计；不折算或忽略异常 |
| 收款提交 | option缓存上限陈旧、等待中已有新增收款、正常订单→取消两态、同账号不同会话、选中对象A→有效B、金额/币种/方式/日期变化 | 读取当前余额且绑定点击时内容；重复/跨表单同订单只一次，失败无记录/日志并保留可修正输入 |
| 并行与历史 | 收款成功意外改变单证状态/纸张、取消变退款、报价保存改旧单证快照 | 合法收款不阻塞单证；金额和单证进度独立；取消原记录不被删除、无虚构退款 |

UI实测需至少覆盖业务员报价编辑→确认→生成及财务登记→余额/记录回读两条路径，增加错误修正/身份只读/取消阻断和USD/EUR核对；1280/1440代表页、控制台、Tab/Enter、错误焦点、减少动效和输入保留。无效金额预览显示“待修正”等含义，不能变成0误导。精度说明靠近字段，错误保留具体行/数量或单价原因；完整原型边界可低频披露，关键操作不被长规则挤压。

测试基于真实动作及Promise/loading，比较失败前后全MOCK；共享helper测试不能代替worker动作。既有12组Node继续跑，涉及修改的JS语法和入口资源检查；浏览器未执行的file://、跨浏览器、真实读屏、PDF/打印、NAS或生产事务单独标未验。最终独立reviewer和UI测评结论以及远端SHA由中枢填写，规划不预写通过。

## 风险与下一轮

两位数量和单价并不保证乘积精确到分，这是H-12明确拒绝一部分输入的现实边界；较高精度/四舍五入必须经正式契约再改显示与计算。当前内存锁只防正常前端并发和延迟动作，不能当作服务端权限、银行入账、数据库事务或财务审计。

本轮实际收益是让数字错误可见且不能进入下一阶段，同时防止陈旧余额/身份写错对象。后续按复盘推进岗位上下文与未提交输入的连续性，或完善正式精度/财务异常文档；不以持续迭代授权自行扩入退款、真实文件、后端和部署。
