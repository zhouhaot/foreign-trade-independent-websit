# 第4轮报价/收款 UI 方案与两轮测评计划

日期2026-10-07，基线`2414905`。本文件为实施前规划与首轮静态测评，不代表第4轮实现/浏览器已通过。H12/H13与精度、资格、内容绑定以`round-04-planning-review.md`为契约；仅本文件和round04设计评审归UI agent，本阶段不改运行代码/Git/HANDOFF或最终DESIGN/JSON。

## 1. 两个页面各自唯一主任务

报价编辑的唯一主任务是：**编辑并校验当前报价的条款、数量/单价与合法合计，然后保存。** 只读客户/业务员/报价号是上下文；不在此页加确认客户或生成订单按钮。客户确认和生成订单继续在已保存报价详情分别按真实状态呈现，沿用已有一次确认，不增加两次或事先批准门禁。

收款登记的唯一主任务是：**给明确的当前订单，按实时币种和余额登记一笔合法收款。** 记录/订单应收/客户欠款是后置参考，不与登记并列成多张摘要说明卡；财务看到登记区，主管仅只读台账，不出现登记按钮。

流程：业务员编辑→合法预览→保存→详情登记客户确认→仅已确认且未生成才生成一次订单；财务选择订单→核对币种/当前已收与余额/资格→输入金额/方式/日期→提交→成功后回读新记录和余额。单证与收款仍并行，旧单证快照不会被当前金额写入覆盖。

## 2. H12/H13的可读表达

H12：普通十进制最多2位小数、至少0.01；数量0.01保留。每行数量×单价必须精确到分，按整数分合计，不隐含舍入。0.01×1.00可用，0.10×0.10为0.01可用；0.01×0.01不足分精度应明确拒绝，不假显示0.00。不能把较早改价算法的整数数量限制错误推广到报价编辑。

H13：取消申请中暂停新增收款，已取消禁止新增收款，旧金额/记录保留；异币种或非法既有记录不能忽略，超收不能被钳成正常结清。此为本轮独立的财务原型假设，不从H09单证暂停推定已有制度，不新增退款/核销/汇率业务。

UI短提示靠近字段：“普通十进制，最多2位小数，至少0.01”；明细旁一条短句“每行金额须精确到分，超出当前精度请调整输入”，完整例子用本地原生details按需展开，不堆独立规则卡。无有效候选时行金额/合计为“待修正”或“无法计算”，不显示0、不保留貌似当前的旧总额、不只合计合法的部分行。

## 3. 首轮静态发现 → 本轮可做小改

| 现状与风险 | 最小UI修正 |
|---|---|
| 数量/单价input没有具体行名称，非法输入Number或0后预览仍像合法金额 | ID与行号/商品/字段关联；“第2行某商品数量”或“单价”具名；数量/单价各自错误，行金额精度错误关联这对输入与该行；非法预览明确待修正 |
| 合计币种文本来自旧报价，改币种可能不同步 | 当前选中启用币种同步行列/合计/详情候选；未知币种不能作为正常预览或默认改成USD |
| 编辑页3个只读身份字段占一整行输入格；条款/备注/明细都纵向堆积 | 报价号/客户/业务员压成清楚的只读上下文行；可编辑必填条款保持常显；备注放明细后，可空白时折叠，已有内容仍提示并默认展开；一张编辑面板、一个保存footer |
| 确认/生成说明以流程长文为主，金额/币种不够集中 | 现有确认框前置报价号/客户/有效期/币种与本次合法合计，再一段简短影响；不加新确认层 |
| 收款选择器可能从URL无效/取消订单自动fallback第一笔可收 | 保留URL指定的对象身份，显示暂停/异常并禁止登记；或明确无可登记对象并让用户主动选择，不能无声换成另一客户订单 |
| 余额来自option缓存，输入上限提示可陈旧 | 当前订单/币种/金额语义都由live数据结果渲染；余额改变或数据异常时给具体原因，失败保留选中订单和输入，不把旧data-out当最终依据 |
| 收款无效/超收被显示成0未收与正常结清 | “数据异常”“超收XX币种”明确显示，禁登记；未知金额为待核对，真实0余额与未知值区分；不能自动折算/退款 |

这些是代码阅读与第3轮文书来源/当前资格的延续，不声称本轮实图已经通过。workers负责实际标记和行为；root整合CSS，不让UI agent覆盖其运行文件。

## 4. 报价页面的任务层级与披露

| 信息 | 分类/频率 | 首屏与容器 | 揭露依据 |
|---|---|---|---|
| 报价号/客户/业务员/待确认身份 | decision-supporting，高 | 标题下紧凑只读上下文，不伪装可编辑输入 | 当前对象必须一直可核对 |
| 有效期/启用币种/贸易术语/付款方式 | action-critical，高 | 单一表单内常显，1440可3列、1280可2/3列按实际宽度 | 必填内容不能藏到默认关闭规则区 |
| 商品名称/数量/单价/行金额/合法合计 | action-critical，高 | 中央明细表最大工作区，金额右对齐与币种明确 | 唯一编辑校验主任务 |
| 每个行/字段错误及当前无法计算原因 | exception-handling，条件性 | 相关字段/行下内联，错误时自动可见 | 不用Toast代替字段定位 |
| 备注 | reference，中低 | 明细后；空时可原生details，已有内容明确“已有备注”并默认展开 | 不能为节省高度隐藏已有商业内容 |
| 精度例子与演示边界 | reference，低 | 字段旁短提示+按需原生details | hidden_now_because=不影响常规合法输入；reveal_trigger=查看输入规则；container=本地details |
| 保存/取消 | action-critical，高 | 同一编辑面板底部右侧，仅一个主保存按钮 | 不引入旁边堆叠说明/统计卡 |

优先只减留白与只读身份输入的占位，保留13px业务文本、38px输入/按钮和完整商品名称。正常2行样例在1280×1000与1440×1000目标保存按钮bottom≤980px；多商品/长条款/错误允许自然滚动或表格局部横滚，不能裁切。若必填字段错误在视口外，提交后滚到并聚焦首个错误；不因重建预览丢输入或改变业务对象。

客户确认与生成订单是详情状态下的下一步：

| 状态 | 主动作与说明 | 不可误报 |
|---|---|---|
| 待客户确认且候选有效 | 登记客户确认，现有一次确认框呈现当前客户/金额/币种 | 不能称已收到真实客户回执或服务端签署 |
| 已确认且未生成 | 生成订单，单次确认展示这份已确认报价的身份/合计与并行支线 | 不在订单列表直接新建，不生成重复订单 |
| 已确认但业务数据失效/内容变更 | 具体阻断原因，重新核对当前详情 | 不用过期合法合计继续生成，也不擅自解锁已确认编辑 |
| 已生成 | 去关联订单，可见订单号 | 不让第二次点击变成第二笔订单；点击不是提交成功 |

金额/币种改变的合法候选B不能偷偷替换曾在确认框展示的A；失败说明“内容已变化，请重新打开核对”，业务原数据不部分写入。完整确认/异步动作由sales worker验证。

## 5. 收款登记页面的任务层级与状态

登记区一次只处理一个订单。最上方为订单选择与短状态；靠近金额显示live币种、总额/已收/当前余额。方式/日期/备注次之，登记按钮底部右侧。余额可以用一条紧凑文字/定义列表，不能扩成3–4张数字卡延后登记。

| 状态 | 必须常显 | 主动作/错误处理 |
|---|---|---|
| 正常可登记 | 明确订单号/客户，订单币种，只读当前已收/余额 | 金额>=0.01、<=live余额且2位精度；方式/真实日历日期合法后登记 |
| 正常余额0/已结清 | 明确“当前无未收金额”，真实0不是未知 | 禁登记，允许主动选择其他订单；历史记录保留 |
| 取消申请中/已取消 | 原订单身份、真实历史金额/状态，暂停原因 | 禁新增；不把金额清零/生成退款，不自动选别单 |
| 异币种/非法记录/超收 | 具体异常与币种/超收数，或“金额待核对” | 禁登记，不能静默忽略记录或显示正常结清 |
| 字段无效 | 金额/方式/日期各自具体原因，输入原文保留 | 聚焦首个问题；不清空日期、备注和合法字段 |
| 提交中 | 当前提交对象和内容稳定，按钮loading/防重复 | 可以最小禁交互，但不能丢值；异步完成重查最新资格和余额 |
| 提交期间条件变化 | 指出当前订单余额/币种/状态/身份变化的可核对原因 | 本次无写入，保留当前输入；同会话允许重新核对后重试，账号退出仍按原清理规则 |
| 成功 | 真实新增收款ID/金额/币种、更新后的已收/余额与记录 | 只有提交实际完成才提示成功，不把演示延时/点击当入账 |

记录、订单应收和客户欠款默认在登记区之后作为参考，可用单一“收款记录/应收核对”页签或原生折叠，而不再堆独立规则卡；若暂沿用现有连续台账，它们的首屏权重应低于登记，明确不同币种独立统计。已有台账/分页/主管只读不能删除。

在1280×1000与1440×1000，普通订单短提示、默认字段下，登记按钮目标bottom≤980px，订单与金额信息不用滚动才能核对。长错误/异常详情可自然滚动，原始事实不裁切。

## 6. 错误与非视觉语义结构

```html
<label for="quote-row-2-qty">第2行露营灯数量</label>
<input id="quote-row-2-qty" inputmode="decimal" aria-invalid="true"
       aria-describedby="quote-row-2-qty-hint quote-row-2-error" value="1.001">
<small id="quote-row-2-qty-hint">普通十进制，最多2位小数，至少0.01</small>
<p id="quote-row-2-error">第2行数量超过2位小数，请调整数量。</p>
<span aria-label="第2行金额">待修正</span>
```

这是语义规范示例，不运行/写入页面。可把具名标签视觉隐藏而保留表头，输入ID稳定唯一；行乘积不足分精度时错误关联数量/单价并说明“该行金额不能精确到分，请调整数量或单价”，不是擅自四舍五入。合计为“待修正”，全局错误摘要只指向相关字段，不重复整段精度教程。

无障碍树：具名页面/当前报价或订单上下文→关联label的条款/订单字段→具名商品行数量/单价/金额→真实合法合计或不可计算状态→字段具体错误→唯一保存/登记动作→后置参考。币种只读但有名称和值，余额变化有简短`role=status`反馈；不把每次键入的整个表格设assertive live，避免金额输入过程中反复朗读。

键盘Tab顺序与DOM任务顺序一致，Enter只在有效且允许的form提交；原生select确认选项不得意外跨流程确认或生成订单。提交错误设置aria-invalid/描述关联并focus；native details Space/Enter正常且不重建输入。Toast只给短结果，完整字段原因保留内联；loading反馈不能替代实际完成。

对应WCAG2.2：1.3.1信息关系、1.4.1颜色非唯一错误线索、1.4.3文本对比、1.4.11控件边界、2.1.1键盘、2.4.7/2.4.11可见且未全遮挡焦点、2.5.8目标尺寸、3.3.1错误识别、3.3.2字段说明、3.3.3可行修正建议、4.1.2名称角色值、4.1.3状态消息。只是设计映射，不提前宣称真实读屏或整体合规。

## 7. 五视角首轮验收计划

| 视角 | 必验情况 | 通过标准 |
|---|---|---|
| 业务员 | 报价合法0.01数量/币种联动；指数/Infinity/超2dp/不足分的行；保存→客户确认→生成 | 非法预览不是0，行/字段错误明确；合法合计同提交；已确认只读；一次确认一次订单；失败保留输入与原数据 |
| 财务 | USD/EUR、金额超余额、余额变化、取消两态、异常旧记录、恰好结清 | 当前对象/币种/余额明确，错误聚焦而不清输入；H13阻断可读，无自动换订单/折算/退款；成功记录及余额真实回读 |
| 主管 | 收款只读、报价确认/生成无权限、暂停/超收核对 | 无越权按钮/业务写入；异常不会被正常结清掩盖；失败理由具体且能核对当前事实 |
| 键盘 | 逐行字段、输入后预览、错误focus、原生订单/币种选择、Enter提交、确认取消 | 名称含行/商品/字段，焦点不丢；预览不重建输入；禁用理由可读；确认取消不丢表单；减少动效保留操作 |
| 真实性 | 0.01×0.01、partial合计、确认A→合法B、实时币种/余额、重复点击/提交成功时机 | 不假0/假合计/假成功；完整候选才提交；旧快照/其它币种/历史/日志不部分漂移；Mock与生产边界明确 |

不足分/超收等缺场景通过隔离测试夹具或真实UI合法构造，不为截图改正式MOCK源码；被UI过滤掉的阻断状态仍要验证URL预选和直接动作，不能把看不到选项当作安全通过。

## 8. 两轮评审与最终证据

1. workers实现后先静态审计候选、字段关联、资格/身份/内容/提交绑定、精度预览和原数据不变；root/独立reviewer使用真实动作与Promise/loading做业务回归。前端锁不是服务器事务。
2. root按固定目标tab/实际1280×1000与1440×1000拍合法编辑、非法预览/字段错误、客户确认/生成、正常收款/暂停/异常各代表viewport图，opacity=1、实际innerWidth断言、scrollY与保存/登记bottom记录。不要重复第3轮fullPage问题或仅按文件名认宽度。
3. UI agent逐张回读图/尺寸并做上述五视角复盘，发现→最小修正→新图/交互复测。特别检查错误文本不会覆盖操作、输入原文保留、完整币种/余额与合计意义；未显示的状态明确用其他证据，不伪报图覆盖。
4. 最终材料独立区分共享helper、worker动作Node、真实UI/角色、键盘特定场景和未验读屏/file/后端领域；必要UI修正Resolved后再给SHIP并同步DESIGN/sidecar。没有新问题不扩大/重复无变更测试。

报价/收款真实主任务两条链要实际完成并回读结果，身份与取消阻断不改变已有单证纸张和并行关系。file://、跨浏览器、真实读屏/缩放、银行/NAS/服务器、真实PDF/打印未经执行仍单独未验。本阶段不自行加入退款、部署、持久化或额外确认制度。
