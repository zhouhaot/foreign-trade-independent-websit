# 第 2 轮 UI 评审与实施方案

日期：2026-10-07。范围：A 方案订单工作区及完整订单详情的进度表达和首屏密度。此文件为设计方案，不代表实现或浏览器验收已通过；暂不修改 DESIGN.md、design.json、业务 JS/CSS、身份、截图或 HANDOFF。

## 1. 问题与本轮目标

第 1 轮真实截图中，单证“未开始”被画成绿色完成勾，源于 `stepsHtml` 将真实状态名称同时作为流程阶段名称。订单工作区在 1000px 高的桌面视口内，右侧常用操作需向下滚动约 180px 才能看全。两项应以局部 helper 和局部间距修正，不重新设计导航、不更改业务状态名、角色权限或并行关系。

唯一主任务仍是：选择一笔订单，同屏核对订单、单证和收款，再进入当前角色允许的业务动作。主场景为基本筛选收起、常规客户名称、无长异常意见的 1280×1000 与 1440×1000 桌面。长说明及展开高级筛选仍允许自然滚动，不能固定高度裁切内容。

## 2. 数据边界：订单汇总与单证版本不能混为一谈

真实状态标签继续输出现有 `tag(o.status)`、`tag(o.docStatus)`、`tag(U.payStatus(o))`；阶段只是可视解释，不写回 MOCK 或产生新业务状态。

`views-docs.js` 的现有汇总逻辑为：无最新单证→未开始；至少两种且全部已通过→已通过；任一最新单证待审核→待审核；其余→制作中。因此“订单待审核”不证明每种单证都已制作或送审。SO2026005 目前商业发票制作中、装箱单已退回，而订单整体标签是制作中。

建议 `views-sales.js` 使用局部 `documentProgressModel(order, latestDocs)` 与 `renderProgress(model)`，供 `orderInspector` 和 `Views.orderDetail` 共同使用。`latestDocs` 应沿用当前业务汇总的最新版本口径（按单证类型选择最新版本）；同一旧版退回不能覆盖新版已通过。仅计算显示模型，不修改原汇总函数、文书内容或版本关系。若仅拿到汇总值而没有单证明细，用保守的“整体状态”投影，不把推断阶段全部打勾。

四个阶段固定为 **制作 → 送审 → 审核 → 可导出**。最后一个是资格，不是已经导出的事实。当前导出只记录演示动作且不生成真实文件；即使 history 有“导出 PDF（演示）”，也不能把节点写成“已实际导出”。

## 3. 单证版本级 phase-label → state 映射

以下映射适用于具体单证版本，或以版本明确命名的进度区；标题旁仍显示真实状态标签。完成勾表示本版本已通过相应过程，不用于“未开始”。

| 真实状态 | 制作 | 送审 | 审核 | 可导出 | 必要解释 |
|---|---|---|---|---|---|
| 未开始／无关联单证 | 未开始，灰编号 | 未开始，灰编号 | 未开始，灰编号 | 未满足，灰编号 | 尚无单证；不出现绿色勾 |
| 草稿 | 当前阶段，紫色编号，文字“草稿” | 未送审，灰编号 | 未审核，灰编号 | 未满足，灰编号 | 草稿尚未送审；不能视作制作完成 |
| 制作中 | 当前阶段，紫色编号，文字“制作中” | 未送审，灰编号 | 未审核，灰编号 | 未满足，灰编号 | 交易字段只读，沿用已有可编辑范围 |
| 待审核 | 已制作，绿色勾 | 已送审，绿色勾 | 当前阶段，橙色编号，文字“待审核” | 未满足，灰编号 | 已送审，不证明已审核通过 |
| 已退回 | 当前阶段，红色/异常编号，文字“待修订” | 需重新送审，中性编号 | 红色异常标识，文字“已退回” | 未满足，灰编号 | 曾送审但本次未通过；取消到审核节点的全绿连接线，明确修订后重送 |
| 已通过 | 已制作，绿色勾 | 已送审，绿色勾 | 审核通过，绿色勾 | **可用，紫色空心编号或可用标识，文字“可导出”** | 不用完成勾，不写“已导出”；可见动作按现有权限和条件决定 |

退回是在原版本上修订或受控生成新版本，由原业务动作决定。本轮只表达“待修订/需重新送审”，不在前端阶段图自行生成版本或改权限。未知状态保留原状态文字，显示“阶段需核对”，不静默当作完成。

## 4. 订单级汇总进度的保守映射

订单面板标题应让用户知道这是**关联单证整体进度**，进度旁真实标签保持不变。低频的逐版本差异交给既有单证详情；面板只补一行必要的异常/数量解释。

| 订单真实 docStatus / 最新版本情况 | 四阶段显示 | 勾与连接线约束 | 一行解释 |
|---|---|---|---|
| 未开始且无单证 | 四节点灰，制作节点文字“未开始” | 零完成勾，零绿色连接线 | 尚无关联单证 |
| 制作中，含草稿/制作中 | 制作当前；送审/审核/可导出中性 | 不证明所有版本制作完成，不画全体制作完成勾 | 含制作中或草稿的实际版本数量 |
| 制作中，含退回 | 制作需修订；审核显示异常标识；其余中性 | 不把退回版本标为审核完成；最新已通过版本事实不被抹去 | “含 N 份退回，修订后重新送审” |
| 待审核，部分类型待审、其它未通过 | 审核当前橙；制作/送审标“已有制作/已有送审”；可导出中性 | **订单级不画制作与送审的全体完成勾**，避免误读所有单证都完成 | “N 份待审核”及必要的制作/退回数量 |
| 已通过，最新集合与汇总一致 | 制作/送审/审核绿色勾；可导出为可用标识 | 第四节点不画已完成勾、不显示已导出 | 最新单证已通过，按版本查看或导出演示 |
| 汇总与最新集合不一致 | 保留汇总真实标签，阶段不推为全完成 | 不重写原数据，不根据一份单证替换整体状态 | 阶段信息需核对；保留既有明细入口 |

若本轮不引入 `latestDocs` 集合，最小实现为：未开始四灰；制作中仅制作当前；待审核仅审核橙色当前，前两节点使用中性“已进入”而不打全体完成勾；已通过前三节点完成、第四可用。相关已退回数量仍可从当前角色选中关联单证辅助提示，但不能据此重算整体状态。这是允许的最小落地方案。

## 5. 订单与收款的异常表达

| 情况 | 保留的数据事实 | 可读表达与视觉约束 |
|---|---|---|
| 订单待执行 | 原状态文字 | “准备执行”阶段当前，未来执行/完成节点中性；不把未执行画完成 |
| 订单执行中 | 原状态文字 | 执行阶段当前，完成阶段中性；订单阶段与单证阶段独立 |
| 订单已完成 | 原状态文字 | 订单执行阶段完成；不自动推定单证已通过或收款结清 |
| 取消申请中 | 原取消状态、现存单证/收款记录 | 订单进度显示暂停/取消审批提示，不给“执行中”当前绿/紫节点；保留其它两条历史事实，不擅自把收款清零 |
| 已取消 | 原取消状态、现存单证/收款记录 | 订单线终止，全流程不能绘成正常完成；保留只读事实。现有已取消订单禁用新增业务动作的规则继续有效 |
| 单证已退回 | 原真实标签或汇总标签 | 红色异常与“修订后重送”文字；不利用颜色把真实状态换成新状态 |
| 未收款 | 实际 received/outstanding/currency | 0% 进度、文字“未收款”、已收0/未收实际金额 |
| 部分收款 | 实际两金额与币种 | 薄荷阅读面仅分组，显示文字“部分收款”；比例可四舍五入，但显示“约 N%”或提供实际金额描述 |
| 已结清 | 实际金额勾稽 | 100% 与“已结清”；不推定订单完成/单证已通过 |

取消申请中是否允许登记收款尚属未确认业务规则，本轮不额外禁用或放行；沿用现有处理并记录假设。可导出资格也不证明已实际导出。三个分区在屏幕和无障碍树都要独立具名，不给统一“整体完成百分比”。

## 6. 最小布局修正与可验证尺寸目标

保留两列、浅导航、紫色抬头、单证浅紫与收款薄荷阅读面。先减留白，不缩小金额、状态文字或点击区。

| 区域 | 第1轮实际样式 | 本轮建议 |
|---|---|---|
| 工作区顶部 | 垂直padding约28–30px，介绍/辅助英文/切换条累计高度较大 | 仅订单工作区上padding20px；eyebrow下间距4px，标题28px，描述仍13px且只保留一句；page-head下间距16px |
| 视图条 | 下间距14px | 下间距10px；记录总数/币种说明与视图切换仍一行 |
| 当前订单抬头 | padding20–24px | padding16–18px，编号20–22px、金额至少17px；不隐藏编号/币种 |
| 客户与来源报价 | padding16px 22px | padding12px 18px，保留客户、来源和交期，长名称自然换行 |
| 三进度外层 | gap12px，padding16px | gap10px，padding12px |
| 单个进度区 | padding18px，标题下间距22px | padding14px，标题下间距12px；步骤标签12px、正文13px不减 |
| 收款金额 | 上间距18px | 上间距12px，保留已收/未收与币种的右对齐 |
| 角色操作及脚注 | 操作底padding16px，脚注底18px | 操作底12px、脚注底12px；按钮仍38px，不把脚注扩大为说明卡 |
| 左列 | 筛选/标题/订单行分隔清楚，内部列表510px | 筛选padding16–18px、标题padding16–18px；保留本页数量/滚动提示，按实际需要将列表max-height调整至430–470px；不删客户/日期/三状态 |

目标：默认协同视图、常规状态下，在1280×1000与1440×1000的`scrollY=0`时，右栏相关操作按钮完整落在视口内，按钮bottom≤980px，页内无横溢。左列分页宜同时可见；若为长客户名、异常说明或已展开筛选，可自然滚动而不隐去内容。不得将固定面板高度、overflow:hidden或降低业务字号作为达标方法。

订单详情头部同一helper表达，原六页签和金额摘要保持；详情页可使用现有横向三分区，并按窄窗口正常折行。为减少列表/详情视觉冲突，本轮统一阶段标签、状态旁注、颜色、可导出资格标识与收款文字值。

## 7. 语义代码示例与无障碍树

以下只是结构规范，root 可适配现有 HTML 字符串 helper。示例为单证版本级待审核，不用于订单汇总未经证实的全体完成：

```html
<section aria-labelledby="doc-progress-title">
  <h4 id="doc-progress-title">单证进度</h4>
  <p>当前状态：待审核</p>
  <ol class="steps" aria-label="单证流程阶段">
    <li class="step done"><span aria-hidden="true">✓</span>制作<span class="sr-only">，已完成</span></li>
    <li class="step done"><span aria-hidden="true">✓</span>送审<span class="sr-only">，已完成</span></li>
    <li class="step warn" aria-current="step"><span aria-hidden="true">3</span>审核<span class="sr-only">，待审核</span></li>
    <li class="step"><span aria-hidden="true">4</span>可导出<span class="sr-only">，条件尚未满足</span></li>
  </ol>
</section>
```

无障碍树应呈现具名独立区域 → 真实状态 → 有序阶段及每阶段文字状态；装饰数字/勾不重复朗读。条件可用是明确文字，不能给第四节点 `aria-current="step"` 或 `aria-checked=true` 来误示已发生动作。阶段为信息，不做Tab停靠，不将其伪装成业务按钮。

焦点流继续为筛选→视图切换→订单按钮→角色动作。选择订单后保留按钮焦点和简短status播报，不把整面板设live；修改进度显示不能使当前按钮丢焦点。收款`progressbar`保留名称和值，可加`aria-valuetext`说明实际币种、已收/总额及约百分比，详情页和分栏使用一致语义。

对应 WCAG 2.2 约束：1.3.1 信息和关系、1.4.1 颜色使用、1.4.3 文本对比、1.4.11 非文本对比、2.1.1 键盘、2.4.7 焦点可见、2.4.11 焦点未被遮挡、2.5.8 目标尺寸、4.1.2 名称角色值、4.1.3 状态消息。这里是设计映射，不是整站合规认证；固定桌面范围尚不能推定400%缩放、读屏或跨浏览器通过。

## 8. 五视角验收清单

| 视角 | 必验场景 | 通过条件 |
|---|---|---|
| 业务主管 | SO2026001待审核；SO2026006取消申请；详情与分栏对比 | 真状态不改名，订单汇总不假定所有版本送审完成；主管入口仍指向最新待审版本；取消未画正常完成线；无自制自审 |
| 外贸业务员 | SO2026003未开始；SO2026007单证已通过但部分收款；表格切换与分页 | 未开始无绿色勾；可导出不等于已导出/已结清；来源报价和三状态保留；没有直接新建订单；未提交筛选输入不丢 |
| 单证员 | SO2026005发票制作中+装箱单退回；新修订草稿；旧退回/新版通过 | 能辨认含退回，修订入口仍是最新退回版本；阶段不抹平草稿/退回差异；核心交易字段只读，原受控修订不变 |
| 财务人员 | SO2026001部分收款；USD/EUR订单切换；已取消/取消申请 | 已收/未收/币种及原金额勾稽保持；收款状态不依赖订单/单证完成；没有新增未经确认取消门禁；比例有文字值，退款/金额更新由本轮财务worker独立验证 |
| 键盘与读屏用户 | Tab/Enter/Space选择订单；切换视图；打开动作弹窗；减少动效 | 焦点可见且不丢失，隐藏视图不进Tab；阶段有完整状态文字、勾数字不重复朗读；status播报简短；不把纯阶段做控件；真实读屏未执行时明确记录限制 |

额外状态用局部渲染夹具验证草稿、已退回、已取消、未知状态；如果原样例缺项，只在测试夹具构造，不为截图改正式 MOCK。列表与详情相同输入须输出相同四阶段语义。

## 9. 两次打磨与证据要求

1. 实现后先进行代码复核：各状态节点/旁注映射、版本选择、聚合状态边界、原业务权限、CSS未裁切、JS语法与相应Node回归。先检查业务真实性再评价观感。
2. root 在固定目标tab、固定1280/1440宽度批次读取真实`innerWidth`，导航回页顶并确认稳定；每页记录实际DOM宽度、scrollY、右栏动作bottom。采用viewport截图；需要底部证据时真实滚动后另拍，不依赖异常fullPage拼接。
3. 图像独立回读尺寸与内容，至少看待审核/未开始/已通过、退回混合/取消及角色动作。未拍到的状态由代码/行为测试明确补证，不将单张主管截图推定为五角色视觉验收。
4. 多视角复审记录具体发现、修正、再测与最终SHIP/仍有阻断；root 更新HANDOFF、DESIGN与sidecar后提交本轮改善说明并推送。当前文档只提供计划，不预写这些完成结果。

参考：现有 `views-sales.js` 的 `orderInspector`、`Views.orderDetail`、`stepsHtml`；`views-docs.js` 的 `syncOrderDocStatus`、单证状态/导出条件；第1轮 `design-review.md`。无新增运行时依赖、后端、持久化或真实导出能力。
