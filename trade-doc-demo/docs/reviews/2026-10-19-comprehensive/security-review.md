## SEC-01：禁用岗位最后一个启用账号会破坏所有角色的登录

| 字段 | 证据与判定 |
|---|---|
| 类型／级别 | 原型缺陷，P1：普通管理操作后核心登录流程不可继续 |
| 状态 | 已在隔离VM复现；中枢通过原生浏览器独立复现，修复尚未由本专题实施 |
| 规则依据 | 用户管理允许禁用非内置管理员，界面承诺“禁用后该账号无法登录”；这不应使其他启用账号的登录页整体失败。退出后应显示可用登录页。 |
| 触发初态 | 原始样例，管理员有效；doc、fin、boss分别只有一个启用账号，sales有两个启用账号 |
| 最短复现 | 管理员进入 `#/system/users` → 禁用 `U004` → 顶栏退出登录 → 确认退出。无需控制台篡改、非法主键或恶意输入。 |
| 预期 | 退出成功；登录页仍可使用；无启用账号的岗位不可选择或明确提示。其他启用账号照常可登录。 |
| 实际 | `U.roleUser('doc')` 返回 `undefined`，`Views.login` 遍历全部岗位时读取 `user.name` 抛 `TypeError: Cannot read properties of undefined (reading 'name')`。此时 `U.currentUser()` 和 `App.user` 均已为null，URL为 `#/login`，`login-role` 未生成，旧管理员页面DOM仍留在屏幕上。 |
| 影响 | 一个岗位不可用导致全部岗位的登录页不可用；无法通过现有正常切岗／登录动作恢复。刷新能还原Mock，但会同时丢失本次演示内存中的业务修改。旧DOM残留不等于仍有管理员写权，系统动作另有身份守卫。 |
| 定位 | `js/views-system.js:36-48` 允许禁用并回读；`js/utils.js:863-865` 只返回启用账号；`js/views-core.js:24-26` 无缺失账号判断，`29`／`49` 同样假设选中账号存在；`js/app.js:284-292` 先退出再调用失败的渲染。 |
| 同类边界 | `js/views-core.js:60-61` 角色提示与 `81-87` 登录提交也解引用缺失账号；修复不能只处理options文字而遗留这两处。 |
| 最小建议 | 登录选项、默认选中、角色提示与提交共用有效启用账号判定；没有启用账号的岗位显示不可选和原因，默认选择可用岗位；提交／排队回调再次核对目标仍存在且启用。保留内存数据与Demo假登录边界。 |
| 验收建议 | 独立禁用doc／fin／boss及全部启用sales后退出，分别验证登录可用、缺失岗位不可提交、其它岗位可重登；另验证提交与回调之间目标账号失效的零写拒绝。不要用刷新抹除触发状态来验收。 |

VM证据中四次 `Views.login()` 复现覆盖doc、fin、boss和sales；第五次走实际 `Actions.logout` 及确认回调。为捕获同步异常而避免Node未处理拒绝，只有最后一组把 `U.withLoading` 的调度替为同步调用，产品退出／渲染回调本身未改。其余组使用实际异步包装。

中枢复核回报：Ego 17在管理员用户页聚焦 `sys-enabled-U004` 后按Space禁用，再退出／确认；回读 `App.user=null`、URL为login、`login-role`不存在、旧 `sys-enabled-U004` 仍存在，并捕获两条 `undefined.name` 错误。这里仅引用中枢独立复核状态，浏览器证据归中枢保存，本专题不冒称自行运行了浏览器。

## 安全候选观察：未升级为已证缺陷

### OBS-SEC-01：Toast把msg作为HTML

`js/utils.js:480-486` 直接把msg拼入 `innerHTML`；隔离sink输入合成标记时确实生成原始HTML。当前调用者含岗位／用户名、内部生成编号、审批title等。审查客户、报价、订单变更理由、单证文本／意见、收款备注的当前写入和展示路径，未找到普通可编辑字段未经处理直达这个sink的路径；合成变异用户姓名／编号后能够构造危险文本，不足以证明当前普通UI可利用。

处理建议是共享Toast默认使用文本节点，并为确需富文本的调用另设显式契约；此处是防御性建议，不是已复现XSS。不定P级、不声称浏览器执行了payload。若后续新增可编辑用户名／编号／导入功能，应重新做可达性分析。

### OBS-SEC-02：部分业务动作不重新查启用用户资料

`js/utils.js:846-851` 直接返回存储的演示身份；`js/utils.js:183-197` 的单证策略及 `js/views-docs.js:516-521` 的动作票据会查角色、模块、actor引用和文档状态，但不按用户表重查enabled。隔离VM打开主管审核确认，再仅把其用户表enabled改为false，确认仍把单证改为已通过。首制单证 `js/views-docs.js:100-109` 和管理员动作 `js/views-system.js:13-16` 则另有用户表核验。

当前单页只能由当前管理员维护用户，普通快捷切岗会替换actor且阻止切入禁用账号；各浏览器页的Mock互不共享。本专题未找到不借助合成变异便可让当前主管被管理员同时禁用而保留同一actor的普通单页操作序列，因此只记录守卫不一致和将来接后端／共享状态时的风险。不能把前端假登录可改存储本身报成生产越权漏洞。真实系统必须以服务端有效会话、启用账号和稳定ID核验，归生产上线缺口。

## 存储、日志与敏感数据结论

- 运行JS中客户端存储仅见 `trade_demo_user`；登录动作写入演示身份的id／name／role／roleName／dept，`U.clearUser` 同时清sessionStorage、localStorage与内存fallback。未发现将业务集合持久化或将输入密码保存到这些位置的代码。
- 当前storage有解析异常fallback，但不做完整schema／用户表验证；损坏或伪造存储的穷举状态未在本专题验证，不把这种Demo设计视作服务端鉴权。
- 对运行JS及index检索未见 `console.*`、`document.cookie`、`eval(`、`new Function`、`fetch(`、`XMLHttpRequest` 或 `WebSocket`；这是源码检查，不是浏览器网络抓包。
- 已跟踪文本扫描324份，623份因扩展名／二进制等范围跳过。未发现受检私钥头、常见OpenAI／GitHub／AWS／Slack token高置信模式；未发现受检凭据文件名。原型公开标注的demo密码不当秘密处理。没有扫描Git历史、ZIP／图片／二进制，也没有连接服务验证任何候选凭据，不能据此声明仓库绝无秘密。
