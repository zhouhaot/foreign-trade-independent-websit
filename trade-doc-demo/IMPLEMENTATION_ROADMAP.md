# 实施路线：A 方案前端与内部业务系统落地

## 概述

更新日期：2026-10-07。当前工作目录为 `E:\foreign-trade-independent-websit\trade-doc-demo`；本文中的文件路径均相对此目录，Git 操作位于上一级仓库。

先交付可体验、可复测的 A 方案静态前端，再逐轮解决单证版本、改价金额和连续业务操作的问题。每轮都保留改进说明、设计与业务评审、实际验证证据、复盘及 GitHub 同步回执；前端演示通过与生产上线通过分开记录。

本文是实施计划，不是已完成清单。已完成内容和实际测试结论以 `HANDOFF.md` 的最新回执为准。

## 已确认要求与实施边界

- 用户最新选择 A：珍珠白、鸢尾紫、薄荷青；轻量导航、订单列表与详情并排，订单/单证/收款独立呈现。
- 面向公司内部约 15 人，未来方向为内网服务器或 NAS；不据此推断设备配置、同时在线人数或可部署的软件。
- 当前仍是普通 HTML/CSS/JS 静态原型：`file://` 可运行、无框架、无构建工具、无运行时外部依赖；业务写入只改内存，刷新复位。
- 销售入口必须从确认报价生成订单。单证与收款并行，主管不能自制自审，管理员没有业务审批权，金额分币种核对。
- 用户授权多个子 agent 协同、缺失数据可明确假设、每轮推送 GitHub、每项改进有文字材料；直到用户手动停止，持续按有价值的迭代队列推进。
- 当前阶段不启动后端代码、数据库、NAS 修改或部署。用户的持续前端授权可以用于前端实现和验证；后续跨入真实系统前，将具体方案与实际环境条件对齐。
- 不为了“每轮有变化”重复改色或制造功能；每轮须对应可复现问题或明确的体验改进。GitHub 同步只报告回读核实的分支及提交 SHA。

## 假设登记

假设用来推进设计和可撤销的原型工作。没有真实输入时，将假设写进当轮材料；不得把假设替换成“用户已确认”或“实际部署已验证”。

| 编号 | 假设或待确认输入 | 用途与允许动作 | 验证/撤销方式 |
|---|---|---|---|
| H-01 | 约 15 人暂按总使用人数理解，同时在线数未知 | 按小团队优先设计单套工作区，不规划微服务；不承诺性能容量 | 获取真实峰值操作人数后调整容量场景 |
| H-02 | 桌面主要为 1280px 及以上 | 用 1280/1440/1920px 评价信息密度，保留现有较窄桌面回归 | 收集员工实际屏幕与浏览器；移动端不默认为本阶段范围 |
| H-03 | 交易数据、账号和公司信息继续用现有 Mock | 前端与业务路径验证，不导入真实业务资料 | 真实数据接入前另行制定脱敏样例、授权与迁移契约 |
| H-04 | 单证只覆盖现有 CI、PL | 精修两类纸张预览与受控修订，暂不增加提单等类型 | 新类型得到实际样张及范围后再加入队列 |
| H-05 | 当前角色/数据可见范围延续现有实现 | 不因新 UI 增加跨业务员记录权限；真实后端权限矩阵作为待办 | 业务负责人确认每种对象的读、写、审与记录范围 |
| H-06 | 原型中无法表达的改价目标应拒绝审批并解释精度原因 | 先阻止“显示通过但金额未达目标”；保持数据与申请状态不变 | 得到数量/单价精度和金额舍入契约后提供精确分摊方案 |
| H-07 | 新版单证暂沿用旧版交易快照进行包装/备注修订 | 防止受控修订悄悄吸收主数据变化；刷新交易快照作为明确动作的后续建议 | 在版本规则确认后决定“新版本保留原交易”与“重新制单采用最新交易”的区别 |
| H-08 | 内网应用服务和数据库最终需要受支持的运行环境 | 只做部署选项比较和条件清单；NAS 暂视为候选载体/文件存储 | 获取设备型号、OS、可用容器/虚拟机、内存/磁盘和备份条件；实际验证后选型 |

H-06/H-07 已进入第 2 轮静态实现，下面记录实际支持范围；这些仍是明确的原型策略，不等于真实企业业务规则已定稿。涉及订单金额、单证真实出具、角色数据范围或部署的业务选择应显式留痕；未知硬件、法律事实和真实身份保持未知，不自行补造。

## 实施步骤

### 阶段 1：A 方案可体验交付（当前轮）

1. **共享视觉与订单工作区**（文件：`css/base.css`、`css/layout.css`、`css/pages.css`、`js/views-sales.js`）
   - 动作：实施浅色窄导航、紫色主要操作、mint 收款分组，订单列表与选中详情并排；状态继续用统一文字标签，金额右对齐并保留币种。
   - 原因：缩短“找订单→看状态→执行下一步”的阅读路径；mint 分组不把“部分收款”改成成功状态。
   - 依赖：A 方案已选；现有五角色和业务契约。
   - 复杂度：中；风险：中，公共 CSS 影响全部页面，缩窄列表可能隐藏关键信息。

2. **多视角测评与修正**（文件：`.impeccable/review/`、`scripts/verify-order-workspace.cjs`、当轮说明）
   - 动作：视觉视角检查留白/对比/长中文/金额；操作视角实点筛选、切换订单、页签、回退与空结果；业务视角检查三条状态、权限和分币种；键盘视角检查选择控件、焦点、搜索、减少动效。
   - 验证：代表页至少覆盖工作台、订单列表、订单详情、CI/PL、应收与审批；1280/1440px 必测。1920px 用于大桌面并排布局，不以屏幕更宽掩盖最低支持尺寸的问题。
   - 原因：Node VM 输出通过不能证明真实页面可读、可点击或不会丢失输入。
   - 依赖：步骤 1；复杂度：中；风险：中。

3. **交付与复盘**（文件：`DESIGN.md`、`.impeccable/design.json`、`HANDOFF.md`、`README.md`、当轮说明）
   - 动作：写每项变化与证据；未实际完成的浏览器项标“未验证”；保留两项历史业务阻断；审查差异后提交并推送，回读远端 SHA。
   - 依赖：审查及当前轮必要回归；复杂度：低；风险：低。
   - 可验证交付：本地能直接打开的 A 方案、当前实现截图和报告、清楚的演示边界、GitHub 对应提交。

### 阶段 2：业务正确性与连续操作（A 方案完成后优先）

每个小轮独立可交付。设计打磨贯穿各轮，先处理会改变单据或金额的缺陷，再扩展页面。

4. **改价精度先防错、再精确**（文件：`js/views-fin.js`、`js/utils.js`、`js/views-sales.js`；建议新增 `scripts/verify-price-approval.cjs`）
   - 动作：先用 AP20260903 建立失败回归，验证目标 27,305.50 USD 与当前两位单价算法的合计偏差；将候选明细与合计校验放在申请“已通过”之前。无法达到目标时提示具体差额/精度原因，订单、申请状态、审批人、日志、收款均不发生半次更新。
   - 进一步方案：明确数量与单价精度、行金额舍入和目标金额规则。建议采用固定精度单位或精确十进制计算；如果增加单价小数位，报价、订单、CI 显示也须同步，不能显示两位单价却用隐藏位算出不同合计。
   - 边界：两位单价与给定数量不一定能表达任意总额，不保证“给最后一行补差”永远有解；不得凭空新增调整行或改数量来凑账。
   - 测试：能精确实现的目标、无法表达的目标、零/负/非有限输入、重复审批、取消、已收金额超过新总额。超收业务规则未确认时提示并阻止该路径，不自行生成退款。
   - 依赖：A 方案完成；复杂度：中；风险：高，属于财务行为，不能仅核对初始 Mock。
   - 可验证交付：错误目标不再被静默标为通过；精度契约与后续实现条件写明。若暂只完成防错，不声称所有改价目标已支持。

5. **单证版本冻结交易快照**（文件：`js/views-docs.js`、`js/views-fin.js`、`js/utils.js`、`js/mock-data.js`；建议新增 `scripts/verify-document-snapshot.cjs`）
   - 动作：为每个演示单证版本建立交易快照，覆盖卖方、买方、订单交易条件、币种、品名/规格/单位/数量/单价；`renderCI`、`renderPL` 读取版本快照，避免动态查主数据改变历史纸张。
   - 创建/修订：样例初始化仅用于给历史演示版本补基线，不能解释为真实历史恢复；修订新版本和重新制单路径分别明确快照来源，严禁悄悄改写 V1。共享字段与方法统一由一个负责人写入。
   - 测试：改客户、商品、卖方及订单金额后 V1 内容仍一致；修订 V2 后 V1 不变；CI/PL 只读/允许编辑字段不变；重复修订不会产生相同版本；送审/审核与收款互不阻塞。
   - 依赖：明确当前轮快照策略；复杂度：中；风险：高，两个版本创建路径都要覆盖，不能只改预览。
   - 可验证交付：可复跑的旧版本不漂移证据与明确的新版本来源规则。

6. **连续销售、单证、收款流程**（文件：`js/views-core.js`、`js/views-sales.js`、`js/views-docs.js`、`js/views-fin.js`；建议新增 `scripts/verify-business-flow.cjs`）
   - 动作：以一笔演示订单贯穿询盘→报价→客户确认→订单，然后分别推进单证与收款；优化下一步入口、确认影响文案、待处理信息与回退。
   - 测试：从动作入口直接调用也不能绕过演示权限和状态；防双击、延迟提交时切换身份、退回原因、修订旧版本保留及收款不改单证状态。
   - 依赖：步骤 4/5 的已交付部分；复杂度：中；风险：中。
   - 可验证交付：两条并行流程的完整演示及跨角色回归，仍明确属于前端原型限制。

### 阶段 3：全页体验收敛与可用性（可按模块继续多轮）

7. **按五类岗位精修**（文件：`js/views-core.js`、`js/views-sales.js`、`js/views-docs.js`、`js/views-fin.js`、`js/views-stats.js`、`js/views-system.js` 与共享 CSS）
   - 动作：每轮只选一个岗位或完整路径，优化待办排序、主次操作、长表格、表单错误、空/错/只读状态；保持 A 的同一套组件和语义色。
   - 建议顺序：业务员找单与报价 → 单证员制作与审核 → 财务登记与核对 → 主管审批与异常 → 管理员配置。
   - 真实入口补全：客户/用户/字典占位可先设计具体内存表单和验证；明确实际实现范围后再替换占位。不能呈现“保存成功”却仅弹 Toast，也不接企业账号或真实主数据。
   - 依赖：阶段 1 和相应业务正确性回归；复杂度：中；风险：中。

8. **状态、规模与键盘细节**（文件：各受影响 `views-*.js`、共享 CSS、`scripts/verify-views.cjs`、当轮浏览器报告）
   - 动作：增加仅用于测试的长名称、大金额、多币种、无结果、较多记录、受限角色与冲突状态；验证筛选/分页/选中详情一致，选择离开当前结果集时行为可解释。
   - 检查：键盘完成关键路径；弹窗焦点返回正确；中文组词不触发跳转；正常和减少动效模式均可操作；不引入常驻动画影响作业。
   - 依赖：每个模块视觉交付；复杂度：中；风险：低到中。
   - 可验证交付：本轮覆盖矩阵、代表截图、实际浏览器结果和未覆盖范围；不称全面无障碍认证或所有浏览器兼容。

### 阶段 4：真实系统的条件收敛与独立实施方案

9. **形成具体生产契约**（建议文件：`docs/production/requirements.md`、`docs/production/deployment-options.md`）
   - 动作：把用户、记录范围、状态机、金额精度、单证版本/导出、审计留痕、真实登录、备份恢复列成业务契约；现有页面只作交互依据。记录峰值人数、数据量与实际设备能力，缺失项标 `NEEDS_USER_INPUT`。
   - 架构建议：小团队优先模块化单体、关系型数据库与独立文件存储；Spring Boot 为现有规划方向。具体运行版本、数据库、容器方案在实施前核查官方支持情况及设备兼容，不现在凭空选定。
   - NAS 分支：具备受支持运行条件时评估承载应用；不具备时可作为备份或文件存储，由独立内网服务器承载服务。备份是否可恢复须用还原演练验证。
   - 依赖：真实范围/设备输入；复杂度：中；风险：高，假登录和前端按钮隐藏不能替代服务端授权。
   - 可验证交付：能用于评审的生产方案、数据模型草案、分阶段实施/回退条件；当前只出文档不新增后端。

10. **未来生产开发按最小业务闭环切片**（位置：未来独立生产目录，具体路径待方案确定）
    - 计划顺序：真实登录与服务端权限 → 客户/商品/询盘/报价/确认生成订单 → 快照单证与审批 → 收款与金额 →真实导出与审计 → 内网测试环境 → 备份还原及小规模试点。
    - 每片须能独立验证数据持久化、重复请求、并发更新和越权拒绝；不一次性引入大架构。前端 Demo 保留原运行方式供设计和回归参考。
    - 真实部署、企业账号、真实业务数据及凭据依具体授权处理；不把“每轮推 GitHub”解释为公开发布真实业务材料或生产部署。
    - 依赖：步骤 9 与阶段范围确定；复杂度：高；风险：高。

## 每轮开发、评测与复盘协议

1. 规划 agent 从真实问题和上轮遗留选择一个可交付目标，写出假设、文件所有权、验收标准和本轮范围；中枢确认依赖后分派。
2. 实现 agent 只改分配文件；涉及业务状态/计算的修复先建立能复现缺陷的回归，再实现。公共模块由单一负责人整合。
3. 每轮设计完成后，从视觉阅读、岗位操作、业务正确性、键盘与布局四种视角评价同一个最终版本。记录“角色、页面、复现步骤、现状、期望、严重级别、证据”；不能只给一个审美分数。
4. 修复阻塞项后，复测受影响路径并让独立 reviewer 复核；截图对应最终提交内容，避免拿修改前截图作为修复证据。
5. 当轮说明逐条记录改进及可验证结果；更新 `HANDOFF.md` 当前状态/待办并追加历史条目，不覆盖旧轮次。
6. 中枢审查差异及待提交文件，提交本轮内容，常规推送后回读 GitHub 分支和 SHA。推送失败单独登记，不能把本地提交写成远端同步成功；不强推覆盖他人修改。
7. 复盘比较“目标/实际结果/问题/原因/下一轮动作”，然后推进最高优先级未完成项。用户停止、工具不可用和权限边界都如实说明；额度授权不代表工具具备重置能力。

推荐当轮材料固定字段：轮次与日期、目标、各 agent 职责、逐项改进前后、修改文件、假设及状态、每个评测视角的问题与解决、测试命令/实际结果/未覆盖、复盘、下一轮队列、本地提交与远端核验 SHA。

## 验证策略

- **语法/资源**：改动 JS 运行 `node --check`，入口资源齐全且本地；`scripts/verify-demo.cjs` 核对初始样例金额和关联。
- **角色/视图**：`scripts/verify-views.cjs`、`scripts/verify-login.cjs`、`scripts/verify-session.cjs`；涉及订单并排选择时追加 `scripts/verify-order-workspace.cjs`。
- **状态变化**：改价、单证快照和业务闭环用阶段 2 计划的专门脚本；不能以初始 Mock 勾稽代替审批后的勾稽。
- **真实浏览器**：`file://` 入口与 HTTP 预览均核查；针对受影响角色与路径检查实际点击、控制台、布局、输入保留、键盘与焦点。现有 `scripts/verify-browser.mjs` 有 Ego Browser 环境前提，使用可用且授权的浏览器工具时明确实际环境和覆盖范围。
- **视觉证据**：1280/1440px 代表页与岗位路径；并排布局可补 1920px。业务截图均使用演示数据，历史截图保留但不算本轮验证。
- **未来系统**：持久化/服务端权限/并发/还原/真实导出仅在对应后端及环境真实建立后测试，当前标未实施。

## 风险与措施

| 风险 | 措施 |
|---|---|
| A 视觉掩盖单证和金额缺陷 | 每轮报告保留上线阻断；下一轮优先业务防错，颜色不改变状态语义 |
| 两位单价不可能表达部分目标金额 | 先校验再提交；失败原子拒绝，明确精度契约后实施，不暗改数量/总额 |
| 快照只冻结订单、漏冻结客户/商品/卖方 | 快照覆盖纸张所有交易字段；测试修改每类主数据后历史版本不变 |
| 多 agent 改同一公共文件互相覆盖 | 明确所有权，共享计算/数据/CSS/交接单写；由中枢整合后回归 |
| 只有脚本通过就宣称设计交付 | 报告分开 Node VM、真实浏览器、目测与业务状态覆盖；未执行项如实标记 |
| 循环改视觉缺少落地收益 | 每轮绑定岗位路径或已复现缺陷，以可操作结果而非提交数量判断价值 |
| 把 NAS、15 人等模糊输入当生产保证 | 保留条件分支；实际硬件核查、峰值场景与恢复演练后再做结论 |
