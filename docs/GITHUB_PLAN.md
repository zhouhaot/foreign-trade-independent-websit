## 仓库与分支建议

建议单仓库包含backend、frontend、docs、部署说明以及经过验证的.claude配置。候选仓库名foreign-trade-order-docs；优先私有，公开须用户明确决定。
main保存可复现基线；feature/任务ID-描述用于开发，fix/任务ID-描述用于修复。单人毕业设计无需额外长期develop分支。
采用Issue/任务卡→功能分支→本地测试→独立AI审查→PR→GitHub Actions→用户授权的合并。AI审查报告不等于GitHub账户的正式审批，不要为单人项目配置无法满足的第二人审批。

## 初次推送操作合同

1. 在本地/连接器确认账号、仓库归属、目标分支、远程是否为空以及可见性。已有仓库先读取内容和历史，不重复git init、不擅自改origin、不强推。
2. 检查git status和差异。加入gitignore、配置样例、说明和经过核验的文档/代码；不要使用未经审查的全量提交。
3. 检查暂存内容和历史是否包含密钥、数据库密码、真实客户/订单数据、日志、数据库备份。私有仓库也不应存秘密。
4. 依据已确认的仓库与分支授权提交/推送。新仓库的建立、可见性与初始化策略需明确；不得推断用户希望公开。
5. 推送后验证远程分支SHA与本地SHA一致，回报仓库、分支、提交和CI状态。推送成功不等于CI通过，更不等于应用已部署。

## CI门槛

GitHub Actions为确定性构建与测试工作流，配置在.github/workflows/。根据任务运行后端测试/构建、数据库集成测试、前端lint/类型检查/测试/构建，以及核心浏览器流程。迁移变更必须跑空库初始化与升级场景。不能把缺少测试脚本或零测试记为成功。
配置密钥和依赖风险检查；Actions使用最小权限，不向不受信任PR暴露密钥，不在首版自动将任何PR代码交给拥有生产凭据的代理执行。
账户与仓库类型支持时，为main启用必需检查、限制强推/删除等保护。私有库的保护能力与套餐有关，不能仅凭创建仓库就声称已强制执行。

## 部署边界

GitHub仓库用于版本管理，GitHub Actions用于构建和检查。GitHub Pages是静态托管，不能直接承载Spring Boot进程与MySQL。演示系统可在本地Docker Compose或另行授权的服务器运行；发布到互联网是独立任务。
