## 阶段审批

P1 和 P2 分别结束后等待业务范围、设计方案确认；这是两个独立工作流。后续已批准范围内的局部修复不反复申请同一授权。新增模块、改变核心金额规则或公开发布属于新的授权/变更范围。

## 单个功能的标准循环

读取已批准需求与接口 → 形成任务卡和验收用例 → 创建隔离分支/worktree → 实现 → 运行本地检查 → 非实现者审查 → 修复与回归 → 总控检查证据 → 在已授权范围内集成 → CI复验 → 更新任务状态。

自动化关卡应实际检查：命令退出码、报告存在且非空、确实发现并执行了测试、关键用例是否覆盖、审查结果是否有效、提交是否与报告一致。模型返回空值或缺字段必须阻塞，不能过滤后当成全部通过。
“所有模型同意”不构成通过条件。固定规则由代码/测试执行；业务争议交由用户决定。

## 协作与冲突

前后端围绕同一已冻结 API 契约并行；数据库迁移与共用 DTO 的变更先由架构负责人串行审核。总控负责集成，不允许各代理互相覆盖文件。worktree 必须以批准的基线 SHA 为起点，不能假定默认分支就是最新集成版本。
单个任务不得夹带“顺手重构”其他模块。跨模块问题开单独任务。需求修改先写变更记录并分析数据库、接口、测试与单证版本影响。

## 恢复与状态

任务状态建议为 DRAFT → READY → RUNNING → VERIFYING → REVIEWED → DONE；可转 NEED_FIX 或 BLOCKED。
模型中断后先读任务、提交状态和实际文件差异，再继续；不能盲目重复执行迁移、收款或外部操作。合并冲突未解决、额度不足、测试未运行时，不得标记 DONE。
保存任务编号、代理角色、实际模型 ID、基线与产出 SHA、改动列表、运行命令、报告路径、问题与下一步。不保存敏感凭据或不必要的原始对话。

## 建议命名的独立工作流

`trade-spec`：预检与需求草案，不写业务代码。
`trade-design`：架构、数据、接口和测试设计，不擅自确认业务。
`trade-feature`：只执行指定已批准任务及必要修复。
`trade-release-check`：全量回归、脱敏与发布就绪检查，不默认 push 或部署。
这些名字是项目建议命名，不是 Claude Code 内置命令。需在本地生成并验证对应脚本之后才可调用。
