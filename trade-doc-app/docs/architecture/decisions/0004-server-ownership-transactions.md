# ADR-0004：服务端归属、授权与原子事务

- 状态：Accepted
- 日期：2026-10-29

## 背景

业务员本人数据、主管全量只读、报价快照和唯一成单必须同时防止越权、部分提交与并发重复。前端隐藏按钮、客户端传入 owner 或先查后写都不是充分保障。

## 决策

真实操作人、岗位和权限只从有效数据库会话及服务端用户记录得到。Route Handler 默认拒绝，业务服务在实际读写前重查操作权限和对象范围；不得接受请求体中的 actor、owner、role、状态、总额或审计时间作为可信事实。

业务员查询必须在 Drizzle 查询条件中限定 `owner_user_id`，列表、详情、搜索、计数和后续导出使用同一范围；不存在与无权对象统一返回 404。主管只有本切片声明的全量读取，不获得销售写权限。复合外键用于保证跨表归属一致，但不替代应用授权。

权威契约中每个多步命令只用一个 PostgreSQL 事务提交业务父/子记录、状态、快照、幂等记录和成功审计；任一步失败全部回滚。采用固定锁序“授权上下文 → 幂等键 → 来源聚合根 → 行/依赖”，在报价聚合上使用行锁或原子 `row_version` 条件串行化竞争。

`quote.inquiry_id`、`quote_confirmation.quote_id`、`sales_order.source_quote_id` 和 `(actor_user_id, idempotency_key)` 等唯一约束由数据库最终兜底。唯一冲突后必须回读并重新鉴权、核对命令指纹/交期，不能直接把冲突当作成功。金额、快照与状态在同一事务内重查和计算。

## 后果

服务层需要显式事务边界，不能把不同请求或独立数据库连接中的多次写入当作原子操作。故障注入、并发成单、版本竞争、跨归属引用和回滚必须由真实 PostgreSQL 场景证明；当前仍全部为 `PLANNED`。

## 历史候选

旧 Spring `@Transactional` 与 MySQL 锁示例只说明过一种候选实现，不决定本工程事务或锁行为。
